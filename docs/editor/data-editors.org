* Data Editors
:PROPERTIES:
:CUSTOM_ID: data-editors

#+begin_quote

#+end_quote

A game ships much of its content as YAML data files that are not levels: input maps, locales, sound banks, HUD layouts, UI layouts, dialog trees, procgen dungeon recipes and themes. The editor edits each of them in its own panel (an actions × bindings table for input maps, a node graph for dialog trees, and so on), but every panel sits on one shared, headless model: =LrgEditorDocument= (=src/editor/lrg-editor-document.h=).

A document holds one file as a YAML tree. The panels, the IPC methods and scripts all edit it through *YAML paths* (=/actions/jump/bindings/0/key=), and every edit is a command on the document's own undo stack, so each open file has its own history. Saving keeps key order, keys the engine does not know and comments. Validation runs the engine's own loader on the text that would be saved, plus structural checks the loader does not make, and returns issues that point at paths and lines.

This page describes the model. The UI of each editor is described in the sections reserved for it at the end.

** At a glance
:PROPERTIES:
:CUSTOM_ID: data-editors-at-a-glance
:END:
#+begin_src c
g_autoptr(GError) error = NULL;
g_autoptr(LrgEditorDocument) doc = NULL;
g_autoptr(GPtrArray) issues = NULL;

doc = lrg_editor_document_new_from_file ("data/controls.input.yaml", &error);

/* one undo step per call */
lrg_editor_document_set_string (doc, "/actions/jump/bindings/0/key", "W", 0, &error);
lrg_editor_document_rename_key (doc, "/actions", "jump", "leap", &error);

/* a drag: many calls, one undo step (same path, same gesture id) */
lrg_editor_document_set_double (doc, "/pieces/health/x", 10.0, 42, &error);
lrg_editor_document_set_double (doc, "/pieces/health/x", 14.5, 42, &error);

lrg_editor_document_undo (doc);

if (!lrg_editor_document_validate (doc, &issues))
	show_issues (issues);           /* errors first, each with path + line */
else
	lrg_editor_document_save (doc, &error);   /* atomic write */
#+end_src

** The model
:PROPERTIES:
:CUSTOM_ID: data-editors-model
:END:
*** One type with a format enum
:PROPERTIES:
:CUSTOM_ID: data-editors-one-type
:END:
=LrgEditorDocument= is a final GObject with a =format= property (=LrgEditorDocumentFormat=: =unknown=, =input-map=, =locale=, =sound-bank=, =hud-layout=, =ui-layout=, =dialog-tree=, =dungeon=, =theme=), not a base class with one subclass per format. Everything the panels and IPC drive (paths, undo, save, reload, line mapping) is the same for every format; the formats differ only in their validator, the skeleton of a new file and a few read helpers. One type keeps the =data.*= IPC methods and the base data-editor panel generic, and the per-format code is a set of static functions selected by the enum. A format the engine does not know (=unknown=) still gets the full editing model, with validation reduced to the YAML-level checks.

*** Properties and signals
:PROPERTIES:
:CUSTOM_ID: data-editors-properties
:END:
| Property | Type | Meaning |
|----------+------+---------|
| =format= | =LrgEditorDocumentFormat= | Picks the validator; detected on open, settable when detection is wrong |
| =path= | string, read-only | The file, or =NULL= while untitled; changed by =save_as= |
| =dirty= | boolean, read-only | The tree differs from the last load or save |
| =read-only= | boolean | Edits and saves are refused; set on open when the file is not writable |
| =can-undo=, =can-redo= | boolean, read-only | For menu sensitivity |
| =undo-limit= | uint | Steps kept, default 256, 0 = unlimited |
| =base-dir= | string | Where relative files (sound bank entries) resolve; =NULL= = the document's directory |
| =reference= | =LrgEditorDocument= | What validation compares against (the source locale) |
| =monitor-file= | boolean | Watch the file with a =GFileMonitor= (off by default) |

| Signal | Arguments | When |
|--------+-----------+------|
| =changed= | path | After every edit, undo and redo step (several for a group), and =""= after a reload. For a set or replace the path is the node's; for insert, remove, move and rename it is the container's |
| =dirty-changed= | gboolean | The document became dirty or clean (also =notify::dirty=) |
| =saved= | path | After a successful save |
| =reloaded= | — | After =reload()= replaced the tree |
| =file-changed= | — | Once per external change on disk since the last load or save |

*** Opening and format detection
:PROPERTIES:
:CUSTOM_ID: data-editors-open
:END:
- =lrg_editor_document_new (format)= creates an untitled document holding the smallest file the format's loader accepts (=actions: {}=, a locale with =code=, =name= and empty =strings=, a dialog tree with one empty node, =preset: midnight= for a theme, ...). Every skeleton passes its own validator.
- =new_from_file (path)= reads the file with comment capture on; a parse error is =LRG_EDITOR_DOCUMENT_ERROR_PARSE= with the line and column. The document is read-only when the file is not writable.
- =new_from_data (text, len, format)= is the same for text; =LRG_EDITOR_DOCUMENT_FORMAT_UNKNOWN= detects the format from the content.

=lrg_editor_document_detect_format (name, text, len)= decides in this order:

1. *A double extension* is an explicit statement: =*.input.yaml= (also =.inputmap=), =*.locale.yaml=, =*.bank.yaml= (also =.soundbank=), =*.hud.yaml=, =*.ui.yaml=, =*.dialog.yaml=, =*.dungeon.yaml=, =*.theme.yaml=, plus the bare names =dungeon.yaml= and =theme.yaml=. =.yml= works too.
2. *The content*: the keys each loader requires or is known by. =actions:= mapping → input map; =sounds:= → sound bank; =pieces:= → HUD layout; =nodes:= sequence → dialog tree; =strings:= or =code:= + =name:= → locale; =generator:= → dungeon; =colors=, =metrics=, =preset=, =accent=, =styles= or =motion= → theme; a root =type:= → UI layout.
3. *The parent directory*: =locales=, =locale=, =i18n=, =lang=, =themes=, =dialogs=, =dialog=, =dialogue=, =input=, =dungeons=, =ui=.

Content beats the directory on purpose: =examples/data/ui/hud.yaml= is a UI layout (it has =type: vbox=), not an =LrgHudLayout= state file.

** YAML paths
:PROPERTIES:
:CUSTOM_ID: data-editors-paths
:END:
Paths follow JSON pointer (RFC 6901):

- A path is =/= followed by segments separated by =/=. =""= and =/= both mean the root.
- A segment is a mapping key or a decimal sequence index (no sign, no leading zeros).
- Inside a segment, =~= is written =~0= and =/= is written =~1=. =lrg_editor_document_path_escape()=, =path_join()= and =path_split()= do the escaping; =/a~1b~0c= is the key =a/b~c=.
- In a setter, a missing last mapping key is created at the end of the mapping, and =-= (or the sequence's length) appends to a sequence. Anything else that does not exist is =LRG_EDITOR_DOCUMENT_ERROR_NOT_FOUND=; walking into a scalar is =WRONG_KIND=; a malformed path is =INVALID_PATH=.

| Path | In an input map | Meaning |
|------+-----------------+---------|
| =/actions= | the actions mapping | |
| =/actions/jump/bindings/0/key= | =SPACE= | key of the first binding of =jump= |
| =/actions/jump/bindings/-= | (setter only) | append a binding |
| =/= | the whole document | =replace (doc, "", text)= swaps everything |

Because the input-map format keys actions by name, an action is addressed by name (=/actions/jump=), not by index; formats that use sequences (dialog =nodes=, dungeon =spawns=, UI =children=) use indices.

*** Reading
:PROPERTIES:
:CUSTOM_ID: data-editors-reading
:END:
- =get_kind (path)= returns =missing=, =null=, =scalar=, =mapping= or =sequence= (=LrgEditorDocumentNodeKind=).
- =get_scalar (path)= returns the text as written (numbers and booleans too); =NULL= for a null or a collection.
- =get_value (path, &value)= types a scalar the way YAML does: a plain =true/false/yes/no/on/off= is a boolean, a plain integer an =int64=, a plain float a =double=, anything else (including every quoted scalar, so ='42'= stays a string) a string. A null gives a =G_TYPE_POINTER= value holding =NULL=.
- =get_keys (path)= returns a mapping's keys in document order; =get_length (path)= the size of a sequence or mapping.
- =get_yaml (path)= serializes a subtree with its comments (copy, the YAML pane); =to_data()= the whole document exactly as =save()= writes it.

*** Line mapping
:PROPERTIES:
:CUSTOM_ID: data-editors-lines
:END:
=get_line (path, &line, &column)= says where a path starts in =to_data()= (for a mapping value: the line of its key), and =get_path_at_line (line)= is the inverse: the deepest node that starts on or before the line. The UI-layout editor uses them to jump from a clicked preview widget to its YAML and back; validation uses them to give every issue a line. yaml-glib does not keep source positions, so the document walks the serialized text with libyaml's event parser and caches the result until the next change.

** Editing and undo
:PROPERTIES:
:CUSTOM_ID: data-editors-undo
:END:
*** Edit operations
:PROPERTIES:
:CUSTOM_ID: data-editors-edit-operations
:END:
Every call below is one undo step (unless merged or grouped) and returns =FALSE= with a =GError= when it cannot apply. A read-only document refuses all of them with =LRG_EDITOR_DOCUMENT_ERROR_READ_ONLY=.

| Call | Effect |
|------+--------|
| =set_string (path, text, gesture)= | A string scalar; written quoted when plain would read as another type (='true'=, ='42'=, ='#ff0000'=) |
| =set_int=, =set_double=, =set_boolean=, =set_null= | Typed scalars. Doubles always read back as floats (=2.0=, not =2=) with the shortest round-trip precision |
| =set_value (path, GValue, gesture)= | The property-grid setter: strings, booleans, every integer width, float, double, enums (written as their nick), unset or =NULL= → null |
| =replace (path, yaml)= | Replace a subtree (or the whole document with =""=) by parsed text |
| =insert_item (path, index, yaml)= | Insert into a sequence; -1 appends; =NULL= inserts a null |
| =move_item (path, from, to)= | Reorder a sequence item |
| =add_key (path, key, yaml, position)= | Add a mapping key at a position in the key order (-1 = end); =EXISTS= if present |
| =rename_key (path, old, new)= | Rename in place: position, value and comments are kept |
| =remove (path)= | Remove a key or a sequence item (not the root) |

A setter replacing an existing node copies the old node's comments (the comment lines above it, the comment after it on its line, the blank line before it) to the new node, so editing a value never drops its comment.

*** How commands work
:PROPERTIES:
:CUSTOM_ID: data-editors-commands
:END:
A command records the container path, the key or index, and references to the node objects it put in and took out; it never copies the tree. Undo swaps the old node back, redo swaps the new one in. Because undo and redo run in strict stack order, the container path always resolves to the same container again. Nodes are never mutated in place: an edit replaces, inserts or removes whole children of a container. yaml-glib can only append to sequences and mappings, so an insert at a position detaches the tail, appends the new entry and re-appends the tail; the container node itself (and its comments) is never replaced.

*** Gesture merging
:PROPERTIES:
:CUSTOM_ID: data-editors-merging
:END:
A drag, a slider or typing in a field produces many edits that the user thinks of as one. The setters take a =gesture_id=:

- Consecutive =set_*= / =set_value= calls on the *same path* with the *same non-zero* gesture id merge into one undo step: the step keeps the value from before the first call and takes the value of the last.
- If the gesture created the key (the first call added it), the later calls merge into that add, so one undo removes the key again.
- 0 never merges. A different path, an undo or redo, a save, or a group boundary ends the merge: the next call with the same id starts a new step.
- The UI allocates a fresh id per gesture (a press-to-release, a focus-in to focus-out).

*** Groups
:PROPERTIES:
:CUSTOM_ID: data-editors-groups
:END:
=begin_group (label)= / =end_group ()= make every edit in between one undo step with that label ("Add binding" = insert a binding + set its key). Groups nest; only the outermost one makes a step, and an empty group makes none. While a group is open, =undo=, =redo= and =save= are refused (=can_undo= is =FALSE=) and the document counts as dirty as soon as the group holds an edit.

*** Labels, limits and dirty tracking
:PROPERTIES:
:CUSTOM_ID: data-editors-dirty
:END:
- Every step has a label for the Edit menu: "Set /actions/jump/bindings/0/key", "Insert /nodes/3", "Rename /actions/leap", "Remove /strings/old", or the group's label.
- =undo-limit= (default 256, 0 = unlimited) drops the oldest steps first.
- Each step carries a serial number naming the state after it, and the document remembers the serial of the state last loaded or saved. =dirty= is "the current serial differs from the clean one", so undoing back to the saved state makes the document clean again, and redoing past it makes it dirty. A merged step gets a new serial (the state changed). Dropping old steps or =clear_undo()= keep the dirty flag as it is.

** Files
:PROPERTIES:
:CUSTOM_ID: data-editors-files
:END:
*** Save
:PROPERTIES:
:CUSTOM_ID: data-editors-save
:END:
=save()= writes =to_data()= with =g_file_set_contents()= (a temporary file renamed over the target, so a crash never leaves a truncated data file), makes the current state clean, ends any gesture merge and emits =saved=. =save_as (path)= does the same to a new file (creating its directory) and makes it the document's file. An untitled document must use =save_as= (=save= fails with =NO_PATH=).

The text is produced by yaml-glib's comment-preserving block writer. What survives and what does not:

| Kept | Lost or normalized |
|------+--------------------|
| Key order of every mapping | Flow style: =[a, b]= and ={k: v}= are written as block sequences and mappings (empty ones stay =[]= / ={}=) |
| Keys and values the engine does not know | Anchors and aliases: =&a= / =*a= are expanded into copies |
| Whole-line comments above a key or item, and the comment after a value on its line | A comment after a one-line flow collection is repeated on every line the collection expands into (a yaml-glib limitation) |
| Blank lines between entries | Comments after the last node of the file |
| Scalar style that matters: ='true'= stays a string, =true= stays a boolean, a plain scalar stays plain while still safe | Quote style: double-quoted scalars are written single-quoted; indentation is always two spaces |
| Multi-line strings (written as literal block scalars) | Document markers (=---=, =...=), directives and tags (=!custom=) |
| | Duplicate keys: yaml-glib keeps the last value at the first key's position; validation warns about them until the next save |

*** Reload and external changes
:PROPERTIES:
:CUSTOM_ID: data-editors-reload
:END:
- =reload()= re-reads the file, drops unsaved edits and the history, makes the document clean and emits =changed ("")= then =reloaded=. A failed reload (unreadable or invalid file) leaves the document unchanged.
- The document remembers the modification time and content of the file at the last load or save. =check_external_change()= compares the time; when it moved (or the file is gone) it compares the content, so a touch or our own save is not a change. On a real change it emits =file-changed= once and keeps returning =TRUE= until the next save or reload. The editor calls it on window focus, and offers "Reload" or "Keep mine" (saving over it).
- With =monitor-file= on, a =GFileMonitor= runs the same check from the main loop whenever the file is written, moved or deleted. It follows =save_as= to the new file.

** Validation
:PROPERTIES:
:CUSTOM_ID: data-editors-validation
:END:
=lrg_editor_document_validate (doc, &issues)= returns =TRUE= when no issue has error severity. Issues are boxed =LrgEditorDocumentIssue= values:

| Field | Meaning |
|-------+---------|
| =severity= | =LrgEditorProblemSeverity= (=info=, =warning=, =error=), shared with the level Problems panel |
| =path= | YAML path of the offending node, best effort (=NULL= when unknown) |
| =line=, =column= | 1-based position in =to_data()=, or 0 |
| =message= | What is wrong, in the engine's words where the engine said it |

Issues come sorted: errors, then warnings, then infos, each in the order found.

*** How the engine loader is run
:PROPERTIES:
:CUSTOM_ID: data-editors-validation-loader
:END:
Validation checks what would be saved: it serializes the document and gives that text to the format's real loader, so a passing document is one the game will load.

- Loaders with a from-memory API get the text directly: =lrg_ui_loader_load_from_data=, =lrg_dialog_tree_new_from_data=, =lrg_procgen_dungeon_new_from_data=, =lrg_theme_new_from_data=.
- Loaders that only read files get a temporary file under =g_get_tmp_dir()= that is deleted right after: =lrg_input_map_load_from_file=, =lrg_locale_new_from_file=, =lrg_hud_layout_load_from_file=, =lrg_sound_bank_new_from_file=. The temporary file's name is replaced by the document's name in every message.
- A loader's =GError= becomes an error issue. Its location is recovered when the message carries one: the UI loader's =children[2].children[0]:= and the dungeon loader's =params.fill-percent:= prefixes become =/children/2/children/0= and =/params/fill-percent= (when that path exists), and =line N, column M= positions are mapped back to a path with =get_path_at_line=.
- Warnings a loader logs while it runs (in its log domain) are captured as warning issues instead of reaching the console, except where the structural checks already report the same thing with a path (input maps).
- Some loaders stop at the first problem. Where the structural checks mirror the loader's rules (HUD layouts, dialog trees), they report every problem with its path, and the loader's own error is added only when they found none.

Duplicate keys found when the file was read are reported for every format as warnings, with the line of the repeat; they disappear from the file at the next save.

*** Structural checks per format
:PROPERTIES:
:CUSTOM_ID: data-editors-validation-formats
:END:
| Format | Engine loader | Structural checks |
|--------+---------------+-------------------|
| Input map | =lrg_input_map_load_from_file= (temp file) | Each action is a mapping with a non-empty =bindings= sequence (else the loader silently drops it). Each binding is a mapping with a known =type= (=keyboard=, =mouse_button=, =gamepad_button=, =gamepad_axis=) and its required field (=key=, =button=, =axis=). Key names are checked against the loader's table (an unknown name loads as no key at all). The same input bound twice, in one action or two, is a warning (modifiers compared order-free) |
| Locale | =lrg_locale_new_from_file= (temp file) | =strings= is a mapping; each entry is a text or a mapping of plural forms (=zero=, =one=, =two=, =few=, =many=, =other=); empty entries are warnings. With a =reference= document: keys it has and this one lacks (warning), keys only here (info), a different number of =%= placeholders than the reference's text (warning) |
| Sound bank | =lrg_sound_bank_new_from_file= on a copy *without* =sounds= (temp file) | The loader would decode every sound, so it only checks the root, =name= and =base_path=. Each sound must be a file name with a known audio extension (wav, ogg, mp3, flac, qoa, xm, mod), and its file must exist, resolved like =LrgSoundBank= does (=base_path= relative to =base-dir=, else the document's directory). Untitled documents without =base-dir= skip the file check |
| HUD layout | =lrg_hud_layout_load_from_file= (temp file) | Only =version= and =pieces= at the root; per piece only =anchor=, =x=, =y=, =locked=, =hidden=; =anchor= a known =LrgHudAnchor= nick; =x= / =y= numbers and only beside an anchor; =locked= / =hidden= =true= / =false= / =yes= / =no= |
| UI layout | =lrg_ui_loader_load_from_data= | The loader is strict (unknown types, properties, values, handlers, includes) and its messages carry the node path and line. =include:= paths resolve against the current directory, since the text is validated from memory |
| Dialog tree | =lrg_dialog_tree_new_from_data= | =id= and a non-empty =nodes= sequence; each node has =id= and =text=; ids are unique; responses have =text= and =next=; every =next= (node, response) and =start= names an existing node; nodes unreachable from =start= (or the first node) are warnings. The loader's linear-scene rule (a node with neither =next= nor =responses= continues with the following node) counts as an edge |
| Dungeon | =lrg_procgen_dungeon_new_from_data= | The loader is strict (unknown keys and parameters, ranges, types) and names the offending key, which becomes the issue's path |
| Theme | =lrg_theme_new_from_data= | The loader is strict (unknown keys, colour roles, metrics, malformed colours). A relative =font:= path is not resolved against the file's directory, since the text is validated from memory |

** Format notes
:PROPERTIES:
:CUSTOM_ID: data-editors-format-notes
:END:
*** Input maps
:PROPERTIES:
:CUSTOM_ID: data-editors-input-maps
:END:
#+begin_src yaml
actions:
  jump:
    bindings:
      - { type: keyboard, key: SPACE }
      - { type: gamepad_button, gamepad: 0, button: RIGHT_FACE_DOWN }
  fire:
    bindings:
      - { type: mouse_button, button: LEFT, modifiers: [SHIFT] }
#+end_src
=input_actions()= lists the action names in order. Renaming an action is =rename_key ("/actions", old, new)=. The engine writer (=lrg_input_map_save_to_file=) iterates a hash table, so a file saved by the game loses its order; saving through the document keeps it.

*** Locales
:PROPERTIES:
:CUSTOM_ID: data-editors-locales
:END:
#+begin_src yaml
code: en
name: English
strings:
  greeting: 'Hello, %s!'
  items:
    one: '%d item'
    other: '%d items'
#+end_src
=locale_keys()= lists the keys of =strings= (a plural entry is one key); =locale_missing_keys (doc, reference)= the reference's keys this locale lacks. The key × language grid opens one document per locale and sets the source language as each one's =reference=.

*** Sound banks
:PROPERTIES:
:CUSTOM_ID: data-editors-sound-banks
:END:
#+begin_src yaml
name: player
base_path: sounds/player/
sounds:
  jump: jump.wav
  land: land.ogg
#+end_src
=sound_bank_resolve (name)= gives the file a sound plays, for preview playback and the missing-file check.

*** HUD layouts
:PROPERTIES:
:CUSTOM_ID: data-editors-hud-layouts
:END:
The player-state file of =LrgHudLayout= (=version= plus =pieces= of =anchor=, =x=, =y=, =locked=, =hidden=). The loader rejects unknown keys, so this is the one format where extra keys are errors rather than preserved notes.

*** UI layouts
:PROPERTIES:
:CUSTOM_ID: data-editors-ui-layouts
:END:
=LrgUILoader= documents (=type:=, =children:=, properties, =on:= handlers, components). The preview-to-YAML jump uses =get_line= on the widget's node path.

*** Dialog trees
:PROPERTIES:
:CUSTOM_ID: data-editors-dialog-trees
:END:
#+begin_src yaml
id: intro
start: hello
nodes:
  - id: hello
    text: Halt!
    responses:
      - { text: Friend, next: friend }
  - id: friend
    text: Pass.
#+end_src
=dialog_nodes()= lists node ids; =dialog_edges()= returns =LrgEditorDocumentEdge= values (=from=, =to=, =response= index or -1, and the path of the =next= value, =NULL= for an implicit chain edge) for the node graph. Targets may name missing nodes; the graph draws those as dangling.

*** Procgen dungeons
:PROPERTIES:
:CUSTOM_ID: data-editors-dungeons
:END:
The recipe format of [[file:../modules/procgen/yaml.org][LrgProcgenDungeon]]. The engine writer (=lrg_procgen_dungeon_to_data=) writes every parameter including defaults; the document writes only what the file has.

*** Themes
:PROPERTIES:
:CUSTOM_ID: data-editors-themes
:END:
The format of [[file:../guides/theming.org][LrgTheme files]]. Colours set with =set_string= are quoted automatically, so ='#7c6cff'= never turns into a comment.

** Engine gaps found
:PROPERTIES:
:CUSTOM_ID: data-editors-engine-gaps
:END:
| Format | From-memory loader | Writer |
|--------+--------------------+--------|
| Input map | no (file only) | =save_to_file= (hash order, drops unknown keys and comments) |
| Locale | no (=new_from_file= only) | none |
| Sound bank | no (and loading decodes audio) | none |

*** Base panel (Save, Revert, Validate, issues list)
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-base
:END:
=LrgEditorDataEditor= (=src/editor/ui/data/lrg-editor-data-editor.h=) is the derivable =LrgContainer= every data editor subclasses. It owns one =LrgEditorDocument= and draws everything the eight editors share, so a subclass only fills its content area and reacts to document changes.

**** Layout
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-base-layout
:END:
From top to bottom:

| Part | Widget names | What it does |
|------+--------------+--------------|
| Toolbar | =data-toolbar=, =data-title=, =data-save=, =data-revert=, =data-validate=, =data-issues= | The format icon (accent), the file name, a warning-coloured dirty dot and the format name; Save (enabled while dirty), Revert, Validate and the issue chip (a green "Valid" check, or the worst severity's icon and colour with the issue count as a badge); then the subclass's own tools (=lrg_editor_data_editor_add_tool()=). Chips compact to icons when the panel is narrow. |
| Banner | =data-banner=, =data-banner-text=, =data-banner-reload=, =data-banner-keep= | Shown when the file changed on disk while there are unsaved edits: a warning-tinted strip with an accent bar, the message, Reload and Keep mine. |
| Content | the subclass widget | Everything between the banner and the issues (=lrg_editor_data_editor_set_content()=). |
| Issues | =data-issues-list= | A list of the last validation's issues, opened by the issue chip or by Validate when there are issues: a severity icon (cross / warning / info in danger / warning / link colours), the YAML path in the mono face, the message, and a "line N" chip. At most six rows tall (40% of the panel). |

The tab title (and the dock tab) is the file name plus " •" while dirty (=LrgEditorDataEditor:title=).

**** Opening, the registry and docking
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-base-open
:END:
- =lrg_editor_data_editor_open (app, path, &error)= takes an absolute path or one relative to the project, reuses an open tab of the same file, otherwise loads the document (=lrg_editor_document_new_from_file()=, file monitoring on), picks the editor type registered for its format and docks it with the panel id ="data:<absolute path>"=.
- *Where it docks*: next to an open data tab (so data tabs stay together wherever they were moved); else next to the code panel when that sits in the viewport's tab stack; else in the center stack, as a tab beside the viewport. (The default layout keeps the code panel in the short bottom stack, too cramped for a table editor.)
- *Registry*: =lrg_editor_data_editor_register_type (format, type)= maps a format to a subclass; =lrg_editor_data_editor_lookup_type()= reads it. The eight built-in editors register themselves lazily on first use, and only when their type really derives from =LrgEditorDataEditor=. Registering again replaces an editor (a plugin can provide its own).
- =lrg_editor_data_editor_can_open (path)= is true for a =.yaml= / =.yml= file whose name and content =lrg_editor_document_detect_format()= recognises and whose format has an editor. Levels, prefabs and projects never match.
- =lrg_editor_data_editor_find (app, path)= returns the open editor of a file; with =NULL= it returns the *focused* data editor: the one that last got a click or a key, else the one opened last. =lrg_editor_data_editor_list (app)= lists them in opening order.
- *Assets panel*: opening (double click, Enter, Open) a file =can_open()= accepts opens it here; a file that does not parse falls through to the usual handling (the code panel or the external editor). The assets panel's constructor also calls =lrg_editor_data_editor_install()=, so the IPC methods exist from start-up.

**** Undo, save, revert, close
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-base-undo
:END:
- Every edit goes through the document; the panel never edits the level. Inside a data editor (focus anywhere in it) the accelerators of =edit.undo= / =edit.redo= (Ctrl+Z, Ctrl+Shift+Z or Ctrl+Y by default) undo and redo the *document's* stack, =file.save= (Ctrl+S) saves the file and =code.close-tab= (Ctrl+W) closes the tab. Text inputs inside the panel keep their own Ctrl+Z.
- The panel is focusable, so a click on empty space in it is enough to route the keys there.
- Save writes the file (=LrgEditorDataEditorClass.save=; the locale editor saves every dirty language), hides the banner and validates again. Revert asks first when there are unsaved changes, then reloads.
- Closing a dirty tab (its dock close button, Ctrl+W, =data.close=) asks Save / Don't Save / Cancel through the editor's dialog protocol. =lrg_editor_data_editor_close (self, TRUE)= closes without asking.

**** External changes
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-base-external
:END:
The document monitors its file. When another program changes it: a clean document reloads silently; a dirty one shows the banner. *Reload* drops the edits and re-reads the file; *Keep mine* hides the banner and the next save overwrites the file. =lrg_editor_data_editor_check_disk()= runs the same check on demand (e.g. on window focus).

**** Validation
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-base-validation
:END:
- Validation runs on open, on save and reload, on Validate, and half a second (canvas time, so tests stay deterministic) after the last edit.
- It is the document's validation (the engine loader plus structural checks) followed by =LrgEditorDataEditorClass.validate=, where subclasses append their own issues (missing translations, missing sound files).
- =lrg_editor_data_editor_get_issues()= returns the issues; the array is refilled in place, so holding it is safe.
- Clicking an issue row (or =lrg_editor_data_editor_activate_issue()=) emits =::reveal= with the issue's path and line; each editor selects and scrolls to what shows that path (=LrgEditorDataEditorClass.reveal=).

**** Writing a data editor
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-base-subclass
:END:
#+begin_src c
/* constructed (): the document and the app are set by now */
G_OBJECT_CLASS (my_editor_parent_class)->constructed (object);
lrg_editor_data_editor_set_content (LRG_EDITOR_DATA_EDITOR (self), my_content);

#+end_src

|----------------+---------+---------|
| =refresh (self, path)= | nothing | Update the content after =LrgEditorDocument::changed= (=""= after a reload or a structural edit). Do not destroy the widget that is being edited from inside this call: defer rebuilds to =step()= (the input map, sound bank and theme editors do). |

**** LrgEditorDataSource: document fields in a property grid
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-base-source
:END:
=LrgEditorDataSource= is an =LrgPropertySource= whose properties are YAML paths of the editor's document, so an =LrgPropertyGrid= edits the file directly:
- =lrg_editor_data_source_add_field (source, name, path, type, label, group, hint, default)=: =type= is string, boolean, int64 or double; =hint= picks the grid editor (="color"=, ="asset"=, ="range:0:1:0.05"=, ="enum-strings:a,b"=); =default= (YAML text) is shown while the path is missing, and such a row reads as default (Reset removes the key).
- Every write is one document command; missing parent mappings (=/colors= of =/colors/text=) are created in the same undo group. =lrg_editor_data_source_bind_grid()= follows the grid's =edit-begin= / =edit-end= so a slider drag or a typing session is one undo step, and a cancelled gesture (Escape) is undone.
- A *read hook* supplies values that are not a scalar at a path (an action's name, a modifier flag that is membership in a sequence); a *write hook* rewrites a value before it is written (a dropped project-relative asset made bank-relative) or does a structural edit itself (rename, type change) and stops the plain write.
- From =refresh=, call =lrg_editor_data_source_document_changed (source, path)= to update the affected rows.

**** IPC methods
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-base-ipc
:END:
Registered by =lrg_editor_data_editor_install()= (idempotent; called by the assets panel and by =open()=). =path= is a file path (absolute or project-relative); when it is omitted the focused data editor is used. Errors use the server's codes: =not-found= for no such editor or node, =invalid-params= for bad paths and arguments, =failed= otherwise.

| Method | Params | Result |
|--------+--------+--------|
| =data.open= | =path= | the editor status (below) |
| =data.list= | — | an array of editor statuses |
| =data.get= | =path?=, =at= (YAML path, default root), =as?= (="yaml"=) | =at=, =kind= (=null=, =scalar=, =mapping=, =sequence=), =value= (typed JSON) for scalars, =keys= for mappings, =length= for sequences, =yaml= for collections or with =as=, =line= |
| =data.set= | =path?=, =at=, =value= (JSON: string, number, boolean, null; an object or array replaces the subtree) or =yaml=, =gesture?= | status + =ok= |
| =data.edit= | =path?=, =op=, =at=, op arguments: =insert= (=index?=, =yaml=), =move= (=from=, =to=), =add_key= (=key=, =yaml=, =position?=), =rename_key= (=old=, =new=), =remove= | status + =ok= |
| =data.undo= / =data.redo= | =path?= | status + =ok= (whether anything changed) |
| =data.validate= | =path?= | =ok= (no errors), =errors=, =issues= (=severity=, =path=, =line=, =column=, =message=) |
| =data.save= | =path?=, =save_as?= | status + =ok= |

| =data.close= | =path?=, =force?= | =closed= (=false= while the unsaved prompt is up) |

The palette also gets =data.save=, =data.revert=, =data.validate= and =data.close= actions (on the focused data editor), and the canvas a ="data"= action group with =data.open(s)=.

*** Input map editor
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-input-map
:END:
=LrgEditorInputMapEditor= (=src/editor/ui/data/lrg-editor-input-map-editor.h=) edits =LrgInputMap= files (see [[#data-editors-input-maps][Input maps]]). The content is a table of actions beside a property grid, with a capture veil over both while it waits for a key.

**** The actions table
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-input-table
:END:
- One row per action, in file order (=lrg_editor_document_input_actions()=): the action name, then its bindings as *chips*: keyboard bindings in the accent colour, mouse buttons in the link colour, gamepad buttons and axes in the success colour, an unknown type in warning. Chip text is readable: =Ctrl+S=, =Shift+Mouse Left=, =Pad A=, =D-pad Up=, =Left Stick X+=.
- A trailing hollow *+* chip adds a binding by capture.
- Clicking a chip selects that binding; clicking the selected chip again (or Enter) re-captures it; clicking the row elsewhere selects the action. Delete removes the selection.
- Toolbar tools: *Action* (add =action_N= with no bindings and select it), *Capture* (re-capture the selected binding, or add one when the action is selected), *Remove* (the selected binding, else the action).

**** The grid
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-input-grid
:END:
- With an action selected: its *Name*. Typing a new name renames the key (=rename_key=, the action keeps its place and its other keys).
- With a binding selected: *Type* (keyboard, mouse_button, gamepad_button, gamepad_axis). Changing the type replaces the binding with the new type's defaults (one undo step). Then per type: *Key* or *Button* (the engine's names as a dropdown) and the *Ctrl / Alt / Shift* modifier flags, which write the =modifiers= sequence (removed when empty); *Gamepad* and *Button*; or *Gamepad*, *Axis*, *Threshold* (0..1) and *Positive*.
- Other keys of an action (a =description=, comments) are never touched.

**** Capture ("press a key or button")
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-input-capture
:END:
- While capturing, the chip reads "Press a key…" and a veil (=input-capture=) dims the content with a prompt; the editor takes keyboard focus.
- The next key press becomes ={ type: keyboard, key: NAME, modifiers: [...] }= with the held Ctrl / Alt / Shift; a lone modifier key waits for the real key. A mouse press on the veil becomes a =mouse_button= binding (left, right, middle, side, extra, forward, back) with the held modifiers. Escape (or the cancel event) leaves without a change.
- Gamepad bindings are set in the grid (the canvas has no gamepad events).
- A capture replaces the binding (or appends one for *+*) as one undo step and selects it.
- API: =lrg_editor_input_map_editor_start_capture (self, action, slot)= (=-1= appends), =cancel_capture()=, =get_capturing()=; =select()=, =add_action()=, =remove_selected()=, =describe_binding()=, and =get_chip_rect()= for tests and automation.

**** Issues
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-input-issues
:END:
An issue under =/actions/<name>/bindings/<i>= selects that binding; one under =/actions/<name>= selects the action.

*** Locale editor
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-locale
:END:
=LrgEditorLocaleEditor= (=src/editor/ui/data/lrg-editor-locale-editor.h=) edits a set of locale files (see [[#data-editors-locales][Locales]]) as one key × language grid.

**** Languages and the reference
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-locale-languages
:END:
- The opened file is the *reference* language (first column, titled "en (reference)"). Every other =.yaml= / =.yml= file in its folder that is a locale is loaded beside it, sorted by file name, as its own =LrgEditorDocument= with the reference set. A column's code is the file's =code:= key, else its file name without the extension.
- Only the opened file is a docked tab; the others are companions: Save writes every dirty language, the dirty dot covers all of them, and Revert / the banner act on the opened file.

**** The grid
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-locale-grid
:END:
- One row per key of any language, the reference's order first, then keys only other languages have. A plural entry (a mapping of forms) gives a row per form, named =key[form]= (=items[one]=, =items[other]=).
- *Missing cells* (the reference has the key, the language does not) are tinted with the danger colour, carry a danger bar on the left and read "missing". A dash marks a key no language must have (only another non-reference language has it).
- Clicking a cell selects it (accent border) and focuses the *edit bar* below the table (=locale-edit-label=, =locale-edit-input=). Enter writes the text and moves down a row, like a spreadsheet; an empty text removes the entry. Writing a missing cell creates =strings= and the plural mapping as needed, as one undo step.
- Toolbar tools: *Key* (a new =new_key_N= in the reference), *Import CSV*, *Export CSV* (file dialogs opened in the locale folder).

**** Undo across languages
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-locale-undo
:END:
Each language has its own document stack. The editor remembers which language each of its writes went to, so Ctrl+Z undoes the last write wherever it went and Ctrl+Shift+Z redoes in order. Edits made to the reference by other means (IPC =data.set=) fall back to the reference's own stack.

**** Missing keys as issues
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-locale-issues
:END:
Besides the reference's own issues, every missing cell is a warning ="'farewell' is missing in fr (fr.yaml)"= with the path =/strings/farewell= and the line of the reference's entry; clicking it selects the first language lacking the key. A companion's own structural issues are listed with its file name in front.

**** CSV
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-locale-csv
:END:
- *Export* (=lrg_editor_locale_editor_export_csv()=) writes RFC 4180 CSV with =,=: a header =key,en,fr,...= and one row per grid row (plural forms as =key[form]=); a missing entry is an empty field; fields with a comma, a quote, a line break or edge spaces are quoted.
- *Import* (=lrg_editor_locale_editor_import_csv()=) reads with =lrg_csv_parse()= and writes every non-empty field of each column whose header is a loaded language code, as one undo step per language; empty fields and unchanged texts are skipped, an unknown code is skipped with a warning. It returns the number of cells written. Exporting and importing the result writes nothing.

*** Theme editor
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-theme
:END:

**** The grid
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-theme-grid

*** HUD layout editor
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-hud-layout
:END:
=LrgEditorHudLayoutEditor= (=src/editor/ui/data/lrg-editor-hud-layout-editor.h=) edits the player-state file of =LrgHudLayout=. The content is a /stage/ beside a property grid: the stage simulates a game screen (1280 x 720 by default; the screen chip in the toolbar cycles 1280x720, 1920x1080, 1024x768, 800x600 and 720x1280) and draws every piece of =pieces:= as a rectangle exactly where the game puts it, through =lrg_hud_layout_resolve()=.

**** What the stage shows
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-hud-stage
:END:
- *The screen* with its thirds drawn as guides and the nine anchor points as dots. The thirds are the regions =lrg_hud_layout_place_rect()= uses to pick an anchor, so the guides show where a drop re-anchors a piece.
- *Placed pieces* (with an =anchor=) as rounded accent rectangles with their id; the selected one gets a thicker accent border, four corner handles and an /anchor line/ from the screen's anchor point to the piece's own anchor point.
- *Unplaced pieces* (no =anchor=: the game's default applies, which the file does not know) stacked up from the bottom-left corner with a dashed outline and the word "default", drawn under the placed pieces.
- *Flags*: a lock icon on locked pieces, an eye icon and 40% opacity on hidden ones.

**** Interaction
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-hud-input
:END:
| Input | Effect |
|-------+--------|
| Click a piece | selects it (property grid shows it); click empty stage clears the selection |
| Drag a piece | moves it; on release the anchor becomes the third holding the piece's centre and the offset follows (the engine's own rule, computed by a scratch =LrgHudLayout= with =place_rect=), written as one undo step "Move HUD piece" |
| Drag a corner handle | resizes the /preview/ rectangle; the anchor is kept and only the offset changes when the anchor point moved (a top-left piece keeps =x=/=y=, a top-right piece grown to the right moves =x=) |
| Arrow keys / Shift+arrows | nudge the selected piece by 1 / 10 units |
| Escape during a drag | cancels it |
| Locked pieces | can be selected but not dragged or resized (the engine refuses to place them too) |

**** Property grid
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-hud-grid
:END:
With a piece selected: /Placement/ (=anchor= as an =LrgHudAnchor= combo, =x=, =y=), /Player/ (=locked=, =hidden=) and /Preview (editor only)/ (=width=, =height=). Changing the anchor converts the offset so the piece stays where it is on screen; =x= and =y= always write the anchor with them (an offset without an anchor is an error of the format). Without a selection the grid shows the file's =version=.

**** Toolbar
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-hud-toolbar
:END:
=hud-add= (Add Piece: =piece-N= at =top-left 16,16=, selected), =hud-reset= (removes =anchor=, =x=, =y= of the selection: back to the game default), =hud-remove= (removes the piece) and =hud-screen= (the screen size chip).

**** Sizes are not saved
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-hud-sizes
:END:
The format has no size: a HUD piece is as large as the game draws it. The editor keeps a preview size per piece (160 x 48 until resized) for the lifetime of the editor, so the anchoring rules can be seen with realistic rectangles; =lrg_editor_hud_layout_editor_set_piece_size()= sets one from code. The loader rejects unknown keys, so the size can never be written into the file.

:END:

*** UI layout editor
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-ui-layout
:END:
=LrgEditorUiLayoutEditor= (=src/editor/ui/data/lrg-editor-ui-layout-editor.h=) edits =LrgUILoader= documents. Three panes side by side: an /outline/ of the built widgets (=LrgTreeView=), the /YAML/ (=LrgTextEditor= with the YAML syntax and line numbers) and a /live preview/ built by an =LrgUILoader= with source tracking on.

**** Text flow and undo
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-ui-flow
:END:
- Typing restarts a 0.35 s debounce timer on the canvas clock (the preview frame's =step=), so tests and replays drive it with frames. =lrg_editor_ui_layout_editor_get_pending()= tells whether text waits; =lrg_editor_ui_layout_editor_apply()= (and the Apply chip) apply it now.
- When it fires, the text is loaded by a fresh loader. On success the new root replaces the preview and the outline is rebuilt (the selection is kept by its path). On failure the previous preview stays and the error is shown.
- Text that is valid YAML is then written into the document with one =lrg_editor_document_replace()= of the root: one undo step per pause in typing. Broken YAML is never written (the document keeps its last valid text); valid YAML the loader refuses (an unknown property, a bad value) is written, so validation, save and undo see what the user typed.
- Any other change of the document (undo, redo, the IPC =data.*= methods, a reload) replaces the pane's text with the document's serialization, keeping the caret line, and rebuilds the preview.

**** Errors
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-ui-errors
:END:
The loader's message (which starts with the node path and ends with "(at line L, column C)") is shown in a banner over the bottom of the preview, wrapped, with a warning icon; the line it names gets a danger band and a gutter bar in the YAML pane. The document's own validation issues are marked the same way (warning or danger colour) while the pane shows the document's text. =lrg_editor_ui_layout_editor_get_error()= returns the message and line.

**** Handlers in the preview
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-ui-handlers
:END:
=on:= entries name C handlers that only the game registers. The preview registers a no-op handler under every name the loader reports as unknown and loads again (up to 64 names per load), so documents with handlers preview without changes; action handlers (=action: prefix.name=) need nothing.

**** Selection across the panes
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-ui-selection
:END:
| From | Does |
|------+------|
| Click in the preview (Pick mode, the default) | picks the deepest widget with a source pointer under the pointer (=lrg_ui_loader_get_source_path()=), selects its outline row and puts the caret on its node (=lrg_ui_loader_get_source_location()=) |
| Hover in the preview (Pick mode) | outlines the widget under the pointer |
| Click an outline row | selects the widget in the preview and puts the caret on its node |
| Move the caret | selects the deepest node starting at or before the caret line (outline row and preview), without moving the caret |
| Pick chip off | clicks reach the preview widgets (buttons press, sliders drag); the selection stays |

The selected widget gets an accent outline, a tint and a type tag in the preview, and its first line a soft accent band in the YAML. Paths are the loader's JSON pointers (="/children/1"=), which are also =LrgEditorDocument= paths, so =lrg_editor_ui_layout_editor_select_path()= and issue paths use the same strings. Widgets of a component body or an included file select their use site; =repeat= / =for-each= copies share their template's pointer.

**** API
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-ui-api
:END:
| Function | Purpose |
|----------+---------|
| =lrg_editor_ui_layout_editor_new (app, document)= | create |
| =lrg_editor_ui_layout_editor_get_text_editor= | the YAML pane |
| =lrg_editor_ui_layout_editor_get_loader= | the loader of the current preview (source queries) |

*** Dialog tree editor
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-dialog-tree
:END:
=LrgEditorDialogTreeEditor= (=src/editor/ui/data/lrg-editor-dialog-tree-editor.h=) edits =LrgDialogTree= definitions as an =LrgNodeGraph= beside a property grid and a play-test pane.

**** The graph
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-dialog-graph
:END:
- *Cards*: one per node, the id in the header, the =speaker= as the category, the start of the =text= (one line, ellipsized) as the body. The start node (=start=, or the first node) is tinted with the success colour.
- *Ports*: an input =in= (several links) and either one output per response (="1  Friend"=, ="2  Foe"=, the response text cut to 18 characters) or a single =next= output for a node without responses. Outputs take one link: wiring an output that has one replaces it.
- *Links* are the =next= references (=lrg_editor_document_dialog_edges()=). The loader's implicit chain (a node with neither =next= nor responses continues with the following node) is drawn dimmed and cannot be deleted (it is not in the file). A reference to a node that does not exist ends at a red card ="missing:<id>"= titled "<id> (missing)".
- *Positions* come from an editor-only =editor: {x, y}= key of the node (the dialog loader ignores unknown keys, so the file still loads in games); nodes without one are laid out in layers: the column is the breadth-first depth from the start node, unreachable nodes get a column after the last. The first layout frames every card.

**** Editing in the graph
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-dialog-edits
:END:
| Gesture | Document edit |
|---------+---------------|
| Drag a wire from an output to a card's =in= | sets that =next= (the node's own or the response's) |
| Drag a wire off a port / delete a link | removes that =next= |
| Drop a wire on empty canvas | adds a node there and links it |
| Drag cards | writes =editor/x= and =editor/y= of each moved node |
| Delete on selected cards | removes the nodes (links into them stay and show as missing) |
| Ctrl+D | duplicates the node's YAML under a free id |

The graph emits its signals in the middle of its own input handling and, for one gesture, in pieces (a reconnect is link-removed then link-added), so the editor queues them and writes them from an idle as one group, "Edit dialog graph": one undo step per gesture, with the queue coalesced (a removal followed by an addition on the same port is just the addition). =lrg_editor_dialog_tree_editor_flush()= writes the queue at once.

**** Property grid
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-dialog-grid
:END:
With one card selected: /Node/ (=id=, =speaker=, =text= (multi-line), and =next= for a node without responses) and one /Response N/ group per response (=text=, =next=); =next= rows offer the node ids. Renaming the id renames every reference and =start= along with it in one undo step. Without a selection: the tree's =id=, =title= and =start=. The rows are rebuilt only when their shape changes (another node, a response added or removed, a node id added or renamed), so typing keeps focus.

**** Toolbar
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-dialog-toolbar
:END:
=dialog-add-node= (a node at the view centre), =dialog-add-response= (a response on the selected node; a node's own =next= moves onto its first response), =dialog-delete= and =dialog-layout= (removes every =editor:= position, one undo step, and frames the result).

**** Play test
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-dialog-play
:END:
The pane under the grid runs the document as it is now through the engine's =LrgDialogRunner= (a fresh =lrg_dialog_tree_new_from_data()= per Play, so it walks what the game would load). Play starts at the start node, From Selected at the selected card. It shows a short transcript, the speaker in the accent colour and the wrapped text; responses are buttons (=dialog-choice-1=, ...; a response whose conditions fail is disabled), a node without responses gets Continue (=dialog-choice-0=), and the last node End. The current node is selected in the graph as the walk goes. The engine runner ends as soon as it enters a terminal node; the pane keeps that node on screen until End. A tree the loader rejects shows its error in the pane.

:PROPERTIES:
:CUSTOM_ID: data-editors-panel-dialog-api
:END:
| Function | Purpose |
|----------+---------|
| =lrg_editor_dialog_tree_editor_new (app, document)= | create |
| =lrg_editor_dialog_tree_editor_get_graph= | the graph (card ids are node ids) |
| =lrg_editor_dialog_tree_editor_get_selected= / =lrg_editor_dialog_tree_editor_select= | the node in the grid |
| =lrg_editor_dialog_tree_editor_add_node= | append a node (returns its id) |
| =lrg_editor_dialog_tree_editor_add_response= | append a response |

*** Procgen dungeon editor
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-dungeon
:END:
=LrgEditorDungeonEditor= (=src/editor/ui/data/lrg-editor-dungeon-editor.h=) edits =LrgProcgenDungeon= recipes: a parameter form beside a map preview.

**** The form
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-dungeon-form
:END:
An =LrgPropertyGrid= over the document, in groups:
- /Recipe/: =generator= (bsp, caves, wfc, drunkard, noise), =width=, =height=, =seed=.
- /Generator: <name>/: every writable, non-construct-only property of the generator class the recipe names, under =params:= (rows are named =param-<property>= so caves' own =connect= and =keep-largest= never clash with the post-processing rows). Switching the generator rebuilds this group.
- /Post-processing/: =cull-min-size=, =keep-largest=, =connect=, =start-exit=.
- /Spawn N/: =kind=, =count=, =min-distance=, =rooms-only= of each spawn rule.

:PROPERTIES:
:CUSTOM_ID: data-editors-panel-dungeon-preview

The editor runs the engine on the serialized document, =lrg_procgen_dungeon_new_from_data()= then =lrg_procgen_dungeon_generate()= with the document's seed, so the preview is exactly the map a game gets for that seed (the tests compare grid hashes). It draws walls (surface), floors and corridors (accent tints), doors (warning), water (link colour), custom tags, room outlines, the start (success dot), the exit (danger square) and the spawn points coloured by kind, with a statistics line (size, seed, rooms, regions, walkable share, spawns); hovering a cell shows its coordinates, tag and room. Cells are drawn as runs of equal tags per row, so large maps stay cheap. A recipe the loader rejects keeps the last map and shows the error over it.

*** Shared pieces of the HUD, UI, dialog and dungeon editors
:PROPERTIES:
:CUSTOM_ID: data-editors-panel-shared-db
:END:
The four editors share an internal property source, =EditorDataFields= (declared under =LRG_EDITOR_DATA_INTERNAL= in =lrg-editor-hud-layout-editor.h=, not public API). Like the public =LrgEditorDataSource= its rows are document paths read and written through =LrgEditorDocument= with the grid's gesture ids, but it also has /virtual rows/ served by callbacks: the HUD editor's anchor (which converts the offset), offset (which always writes the anchor) and preview size, and the dialog editor's id (which renames references). Rows take any =GParamSpec= (enums, unsigned 64-bit seeds, cloned generator properties).

=tests/test-editor-app-data-2.c= drives the four editors through the canvas of a headless app: HUD drags (re-anchoring, one undo step, a locked piece that does not move, save then =LrgHudLayout= reading the placement back), corner resizes keeping the anchor, the anchor row keeping the rectangle, toolbar add/remove; UI preview clicks selecting the YAML path and caret line, outline clicks, caret moves, pick/interact, typed text applied after the debounce, broken YAML keeping the preview and the document, a loader error written and marked, undo restoring the text; dialog wires dragged between ports, card drags, missing targets and their issues, grid rename with references, Add Response, Delete on cards, the play test through Continue and End; dungeon preview hashes against the engine, Randomize and its undo, form rows (width, generator switch), a rejected recipe and Add Spawn; and a paint pass over all four.
