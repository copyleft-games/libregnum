This page compares =lrgeditor= and the libregnum engine underneath it with the editors of Godot 4 (4.6), Unity 6 and Unreal Engine 5. It is written against the source tree at v0.8.1, not against marketing copy: every "have" for libregnum names the module or file that provides it, and every "missing" was checked with a search of =src/= before it was written down. The other engines' columns describe stock features of the editor and its first-party packages or plugins (Unity packages such as Addressables or Timeline count; Asset Store and Fab content does not).

The goal is not to clone any of them. It is to know, area by area, what a game team would miss when moving from one of those editors to =lrgeditor=, which of those gaps are editor work (UI over runtime that already exists) and which need engine work first, and in what order to close them.

** Summary
:PROPERTIES:
:CUSTOM_ID: summary
:END:
*** Where libregnum stands
:PROPERTIES:
:CUSTOM_ID: where-libregnum-stands
:END:
libregnum is a broad engine with a young editor. The runtime covers far more ground than the editor exposes: forward lighting with a light grid and cascaded plus point-light shadows (=LrgLightSet=, =LrgShadowRenderer=), a sky dome, weather and day/night, a post-processing stack, skinned glTF models, a skeletal animation system with state machines, blend trees and IK, CPU particles, 2D and bounded 3D physics, grid, triangle and voxel-baked navigation meshes, behaviour trees, an audio mixer graph with positional voices, a retained UI toolkit with a YAML loader, tilemaps, localisation, save games, mods, VR, video, networking and MMO services. Through v0.8.0 the editor authored levels of nodes (primitives, mesh and sprite assets, lights, cameras, audio emitters, prefab instances, components, scripts), painted tilemaps, keyframed scalar timelines and ran play-in-editor.

v0.8.1 rebuilds the editor on the retained =src/ui= toolkit and closes the editor-side gaps that need no new runtime: split and quad viewports, real engine lighting/shadows/sky/post in the viewport, render modes, live inspection while playing, a profiler panel, a reflected property grid, linked prefabs with overrides, stable asset GUIDs with importer settings, a code editor panel, git status, and eight data editors (input maps, locales, sound banks, themes, HUD layouts, UI layouts, dialog trees, procgen dungeons).

The honest headline is that after 0.8.1 the editor is close to the engine's ceiling in several areas; further progress in rendering, animation, VFX, physics, AI, level streaming and shipping is gated on engine work, not on editor work. The largest single structural gap is that the runtime has no 3D entity model that matches the authoring model: =lrg_level_instantiate()= (=src/editor/lrg-level-instantiate.c=) creates one 2D =LrgGameObject= per node with only the X/Y position, adds every node flat to the world, and materialises components and scripts, while visuals other than primitives (meshes, sprites, lights, cameras, audio emitters, prefab links) have no runtime counterpart. The editor can show a lit 3D level; a shipped game has to re-interpret the =.rlevel= itself.

*** Unique strengths
:PROPERTIES:
:CUSTOM_ID: unique-strengths
:END:
- *Automation first.* Every editor action, node edit, play control and screenshot is reachable over a JSON-lines IPC socket, the kubectl-style =lrgeditorctl= CLI, an MCP server (=lrgeditorctl mcp= or =lrgeditor --mcp=, headless) and the first-party Emacs package. None of the three comparison editors ships an MCP server or a stable external control protocol in the box; Unreal's Python and Remote Control API come closest.
- *Headless editor.* =lrgeditor --headless= / =--validate= runs the whole editor core without a display, so CI can validate, edit and save levels; the editor core (=src/editor/*.c=) has no GUI dependency at all.
- *Plain-text formats.* Levels (=.rlevel=), prefabs (=.rprefab=), projects (=project.ryaml=), editor settings, UI layouts, themes, input maps, locales, sound banks and the new =.meta= sidecars are YAML: diffable, mergeable and hand-editable. Godot's =.tscn= is text too; Unity YAML scenes and Unreal's binary =.uasset= are far less pleasant to merge.
- *FOSS, AGPL-3.0, C/GObject.* No royalties, no seat licences, no closed runtime. Every public type is introspectable, so games and tools can be written in Lua, Python (PyGObject), GJS, crispy C or plain C against the same API.
- *Breadth of gameplay modules.* Inventory, quests, dialog, economy, deckbuilder, idle, procgen, replay and rollback, MMO services, analytics, achievements, accessibility: Godot and Unity leave these to plugins; Unreal has only some (Gameplay Ability System, Common UI).
- *Editor as a library.* =LrgEditor= is host-agnostic (=LrgEditorHost=), so the same undo/redo/selection core can run inside cmacs, inside a game (an in-game level editor) or as =lrgeditor=.

*** Biggest gaps
:PROPERTIES:
:CUSTOM_ID: biggest-gaps
:END:
1. *Runtime 3D scene model.* No runtime representation of the authored 3D hierarchy (transform parenting in 3D, mesh/light/camera/audio components); see [[#engine-runtime][Runtime systems]].
2. *Materials and shaders.* No material asset, no user shader asset, no shader or material graph, Blinn-style forward shading rather than PBR, no image-based lighting.
3. *Global illumination.* =LrgLightProbe= and =LrgLightmap= are 2D helpers (a CPU sampler of =LrgLight2D= colours and an RGB overlay image); there is no 3D lightmap baker, probe volume or real-time GI.
4. *Data formats for authored systems.* Particles, animation state machines and blend trees, behaviour trees, post stacks and physics bodies can be built in code (and single objects from a flat =type:= YAML document via the registry), but have no structured file format, so they cannot be edited, saved or diffed as assets.
5. *Animation pipeline.* glTF clips play through =LrgModelAnimator= (crossfades only); the state machine/blend tree/IK stack runs on =LrgSkeleton= and is not wired to skinned glTF meshes; no retargeting, no sequencer.
6. *Shipping.* No export/packaging pipeline: =rres= packs can be read (=LrgAssetPack=) but nothing cooks a project into a distributable build.
7. *Debugging.* CPU section profiler only; no script debugger, no script hot reload, no GPU, memory or network profilers, no frame debugger.
8. *Level scale.* No sub-levels, level instances or streaming (terrain chunks and portal sectors exist as building blocks).

** Recommended roadmap
:PROPERTIES:
:CUSTOM_ID: roadmap
:END:
Ordered by dependency first, then by how many rows each item unlocks.

1. *3D runtime scene model* (0.9.x, XL). Everything 3D in the editor (play-in-editor, timelines, live inspection, lights, audio emitters, prefabs at runtime) currently stops at a 2D game object. Doing this first means every later feature has one runtime target instead of the game re-reading =.rlevel=.
2. *Composite YAML loader + format writers* (0.9.x, M + S). Cheap, and it unblocks the particle, animation, BT, post and physics formats and makes the 0.8.1 data editors save through the engine.
3. *Material assets, user shaders, PBR, cubemap sky + IBL* (0.9.x, L). The single most visible quality gap; glTF assets are authored for metallic-roughness and currently look wrong.
4. *Debug draw + physics debug draw + nav agents* (0.9.x, S + M). Small items with high daily value for gameplay programmers.
5. *Animation wiring* (0.9.x, L). The state machine, blend trees and IK already exist; connecting them to skinned glTF meshes turns three engine-only modules into an editable feature.
6. *Runtime import settings and runtime prefab references* (0.9.x, M). Closes the "editor shows something the game does not" holes left by 0.8.1.
7. *Script hot reload, memory profiler, GPU timings* (0.9.x, M). Iteration speed.
8. *Export/packaging pipeline* (0.10, L). Needed before anyone ships; depends on runtime import settings.
9. *3D physics decision and implementation* (0.10, XL). Needs a maintainer decision (below) before work starts.
10. *Lightmap baker and SH probes, LOD, decals, sub-levels and streaming, debugger* (0.10). Large but well-understood; they matter for content-heavy games.
11. *Visual scripting runtime, GPU particles, retargeting, sequencer* (1.0 or later). The UI pieces exist; the runtime and formats are the work, and the user base for them is smaller in a C/GI-scripted engine.

** Open questions for the maintainer
:PROPERTIES:
:CUSTOM_ID: open-questions
:END:
- *Runtime model:* should the 3D runtime be a 3D transform component on the existing =LrgGameObject= (which derives from graylib's 2D =GrlEntity=), a new 3D entity type, or should =LrgScene= / =LrgLevel3D= become the 3D runtime and =LrgWorld= stay 2D?
- *3D physics:* extend =LrgDynamicsWorld= in C, or bind Jolt (C++, MIT) through the JoltC wrapper and accept a C++ build dependency?
- *Renderer direction:* stay forward (light grid) and add PBR/IBL, or plan a deferred or clustered path that also enables decals, SSAO and buffer debug views? GL 3.3 has no compute shaders, which limits GPU particles and clustered culling.
- *Material format ownership:* does =LrgMaterial3D= become the material asset, or is it kept as the inline authoring struct with a new =LrgMaterial= for runtime batches?
- *Visual scripting:* worth building given GI scripting in Lua/Python/GJS, or keep =LrgNodeGraph= for data graphs (dialog, BT, animation, shaders) only?
- *Platforms:* is macOS or Web a 1.0 goal, or is Linux + Windows the supported set?
- *Release cadence:* the rendering and runtime-model items are each larger than 0.8.1; should 0.9 be a single runtime-model release with the rest following in point releases?
