This page covers measuring frame cost (=lrg-bench=), the rules the engine's per-frame code follows, the framerate pass of October 2026 (what changed, with numbers) and the hitch pass that followed it (frames that occasionally cost far more than the median). Editor-specific frame cost is in [[file:editor/editor-app.org][the editor app page]]; graylib's own rules are in graylib's =docs/best_practices.org=.

** Measuring: lrg-bench
:PROPERTIES:
:CUSTOM_ID: lrg-bench
:END:
=bench/lrg-bench.c= runs CPU-bound scenarios with the frame cap off in a 320x240 window, small on purpose so fill rate stays out of the numbers and the engine's own per-frame work dominates. For each scenario it prints the whole-frame mean, median, p95 and FPS, and the *work* median: the scenario's update and draw submission alone, without the driver's flush and buffer swap. Under a software rasterizer (Xvfb + llvmpipe) the work column is the one that tracks engine changes; whole-frame times are dominated by the rasterizer.

#+begin_src sh
make -C bench                                    # bench/build/release/bench/lrg-bench
make -C bench run                                # all scenarios (Xvfb when DISPLAY is unset)
make -C bench run BENCH_ARGS='-s tilemap -f 600' # one scenario, longer
LRG_BENCH_XVFB=1 bench/run-bench.sh bench/build/release/bench/lrg-bench -o yaml   # private Xvfb even with a display, YAML out
bench/build/release/bench/lrg-bench -l           # list scenarios
#+end_src

** Rules for per-frame code
:PROPERTIES:
:CUSTOM_ID: rules
:END:
- *No heap values in draw loops.* =GrlColor=, =GrlVector2/3=, =GrlRectangle= are plain structs: declare them on the stack (or =static const= for constant colours) and pass addresses. Use the non-allocating getters: =grl_entity_get_origin_xy()=, =grl_font_measure_text_xy()=, =lrg_tileset_get_tile_rect_to()=.
- *Cull before submitting.* =src/graphics/lrg-draw-cull-private.h= gives the visible area of the z = 0 plane (=lrg_draw_cull_visible_rect_2d()=) and frustum tests for 3D boxes, both read from rlgl's live projection x modelview x transform, so they are right inside any camera, render target, letterbox viewport or shadow pass without the caller passing anything in.
- *Cache what does not change between frames.* Sort orders (=LrgWorld=), measured text (=LrgLabel=), uniform locations, light grids, instance buffers and GPU meshes are kept and invalidated on change, not rebuilt per frame.
- *Batch-friendly order.* raylib flushes its batch whenever the texture, shader, blend mode or scissor changes; group draws by texture.
- *No per-frame logging or string formatting* on paths that run every frame.
- *No blocking I/O on the frame thread.* File writes that fsync, network requests and retries with sleeps go to a worker thread (the save manager's writer, the HTTP analytics sender); the frame thread only collects state. Results come back without a main loop (the standalone game loop does not iterate a =GMainContext=): through an explicit flush or the next call, or a main-context source where one is iterated.
- *Keep scratch buffers across frames.* A per-frame =g_new= / =g_array_sized_new= of 128 KiB or more is an =mmap=, page faults and an =munmap= every frame (glibc's mmap threshold); keep the array on the object and reset its length.
- *Membership changes are O(1) or O(log n) per object.* Many objects come and go in the same frame (explosions, wave spawns, level streaming); a linear search per removal turns that frame into O(n·k).

** Build flags
:PROPERTIES:
:CUSTOM_ID: build-flags
:END:
Release builds (=DEBUG=0=) of libregnum and graylib use =-O2 -fno-semantic-interposition -DG_DISABLE_CAST_CHECKS=: calls between a library's own functions can be inlined although it is built =-fPIC=, and GObject cast macros compile to plain casts (=g_return_if_fail()= argument checks stay on). =DEBUG=1= builds keep full cast checks. The bundled raylib is built at =-O2= (its Makefile defaults to =-O1= for desktop release builds; graylib passes =CUSTOM_CFLAGS=-O2=, raylib's sources are unchanged). At =-O2= raylib's own =rcore.c= emits three =-Wstringop-truncation= warnings; they are raylib's, like the =m3d.h= warning that was already there.

The extra inlining lets GCC see through more calls, which surfaced latent paths where an output argument stayed unset after a failed =g_return_if_fail()= or a constructor's =NULL= return was dereferenced; those were fixed at the source, not silenced.

** The October 2026 framerate pass
:PROPERTIES:
:CUSTOM_ID: framerate-pass
:END:
Measured with =lrg-bench= under Xvfb + llvmpipe on a 20-thread Alder Lake laptop, 300 frames per scenario, before (master =46a6583=) and after. Work = scenario CPU time per frame (median); frame = whole-frame mean.

| Scenario        | Before                     | After                     | Change                               |
|-----------------+----------------------------+---------------------------+--------------------------------------|
| =tilemap=       | work 52.3 ms, frame 53.6 ms | work 1.2 ms, frame 1.9 ms | ~28x (viewport culling)             |
| =ui-labels=     | work 3.07 ms, frame 4.19 ms | work 1.50 ms, frame 2.65 ms | 2x (graylib text layout)          |
| =ecs-sprites=   | crashed                    | work 0.95 ms              | fixed (=lrg_world_draw= NULL vfunc)  |
| =particles=     | crashed                    | work 0.12 ms              | fixed (pool realloc under live list) |
| =grass=         | frame 69.2 ms              | frame 14.1 ms             | ~5x (persistent instances, culling)  |
| =world-shadows= | frame 135.7 ms             | frame 74.8 ms             | ~1.8x (frustum culling per pass)     |
| =billboards=    | frame 12.4 ms              | frame 7.9 ms              | cluster culling                      |
| =terrain=       | frame 11.0 ms              | frame 8.7 ms              | chunk/patch culling                  |
| =shapes-round=  | frame 37.1 ms              | frame 27.6 ms             | cached GPU meshes                    |
| =light-grid=    | 0.615 ms                   | 0.213 ms                  | skip unchanged rebuild/upload        |
| =graylib-draw=  | work 7.5 ms (raylib -O1)   | work 5.4 ms               | raylib at -O2                        |
| =animator=      | 6.86 ms                    | 0.31 ms                   | single-pass skeleton, cached track maps |
| =physics=       | 4.17 ms                    | 0.24 ms                   | sort-and-sweep broadphase            |
| =event-bus=     | 5.42 ms                    | 0.87 ms                   | mask filter before snapshot          |
| =transforms=    | 2.63 ms                    | ~0.85 ms                  | one parent walk, no allocation       |
| =object-pool=   | 3.04 ms                    | 1.6 ms                    | O(1) release, reused snapshot        |
| editor frame (5050 nodes, 4000 log lines) | 11.8 ms | 0.35 ms         | console/hierarchy culling and caches |

What changed, by area:
- *2D*: tilemap draws only tiles that can land in the viewport; =LrgWorld= keeps its draw order between frames (stable by z-index then insertion) and insertion-sorts it in place; sprite components and =GrlSprite= draw without allocating; =LrgGame2DTemplate= paints letterbox bars instead of a second full-window clear; labels cache their measured size; text everywhere goes through graylib's O(1)-lookup layout.
- *3D*: frustum culling in static batches, terrain, water, billboard clusters and grass, for the camera and every shadow pass; uniform locations cached per shader; the light grid rebuilds and uploads only on change; grass keeps a persistent instance buffer; spheres, cylinders and cones draw cached GPU meshes.
- *Simulation*: skeletons compute world poses in one parent-before-child pass without allocating; animators cache track-to-bone maps and binary-search keyframes; physics uses a sort-and-sweep broadphase with the same pairs in the same order; the event bus filters by mask before snapshotting listeners; transform components walk the parent chain once; object pools release in O(1); portals reuse their scratch tables. Details in each module's page.
- *Editor*: see [[file:editor/editor-app.org][Frame cost]].

Bugs fixed on the way (each has a regression test):
- =lrg_world_draw()= crashed on any world with objects: =LrgGameObject::draw= chained up to =GrlEntity='s =NULL= draw vfunc. It now draws the object's enabled sprite components (=/ecs/world/draw-order=).
- =LrgParticleSystem= let its pool grow past =max-particles=, reallocating the particles under its active list (a crash once emission outran the capacity). The pool is now fixed at =max-particles= (=/particles/system/respects-max-particles=).
- =GrlSprite= =flip-h=/=flip-v= were negated twice and never flipped.
- =GrlScene= ignored z-index changes made after an entity was added (graylib =/scene/draw-order-follows-z-index=).
- Skeleton chains deeper than 100 bones listed child-first never converged.
- A collision handler that removed a body mid-step could make the physics step use the freed body.
- The portal system emitted =visibility-changed= on every update, not only when the visible set changed.

Behaviour changes to know about:
- =lrg_physics_world_step()= simulates at most 5/60 s per call (at least 5 fixed steps) and drops the excess, so one slow frame cannot snowball into ever longer steps.
- The event bus captures listener masks at the start of an emission, as it already did priorities.
- =max-particles= is now a hard cap on a particle system's live particles (it was documented as one but not enforced).
- Solid =LrgSphere3D=, =LrgCylinder3D= and =LrgCone3D= draw cached meshes with raylib's default shader, like =LrgIcosphere3D= and =LrgTorus3D= already did, so a =BeginShaderMode()= around them no longer applies; their output can differ from the old immediate-mode path by a pixel at a triangle edge (GPU vs CPU vertex transform).

** Lows and jitter: the core-affinity and timing pass
:PROPERTIES:
:CUSTOM_ID: lows-pass
:END:
=lrg-bench= reports, per scenario, the frame rate, the *1% and 5% lows* (frame rate of the mean of the slowest 1% / 5% of frames), p99 and max frame time, *jitter* (standard deviation of the change in frame time from one frame to the next) and the scenario's own work time; frame times are intervals between consecutive returns from end-drawing. =--fps N= caps the frame rate and the =pacing= scenario measures the limiter (raylib's limiter holds 60.0 fps with 0.045 ms jitter here, so it was left alone).

On a hybrid CPU the largest source of lows was the scheduler moving the main thread between performance and efficiency cores. =LrgEngine= now keeps it (and the driver threads started after it) on the performance cores ([[file:modules/core/engine.org::#performance-cores][details]]). Same binary, =--no-pin= vs default, Alder Lake laptop, Xvfb + llvmpipe:

| Scenario        | fps (no pin -> pinned) | 1% low          | jitter          |
|-----------------+------------------------+-----------------+-----------------|
| =ecs-sprites=   | 366 -> 430             | 205 -> 356      | 0.47 -> 0.10 ms |
| =tilemap=       | 574 -> 558             | 342 -> 422      | 0.29 -> 0.23 ms |
| =physics=       | 2943 -> 4675           | 1661 -> 2857    | 0.08 -> 0.04 ms |
| =gui=           | 847 -> 1399            | 445 -> 717      | 0.31 -> 0.16 ms |
| =world-shadows= | 28.2 -> 31.2           | 20.8 -> 26.5    | 4.78 -> 1.13 ms |

Timing fixes in the same pass:
- *Delta snapping* (=LrgGameTemplate:snap-frame-delta=): with the default 1/60 s fixed step, frame deltas within 0.2 ms of a whole number of steps are snapped, so a 60 Hz display gets exactly one fixed update every frame instead of an occasional 0 or 2 (stutter at a steady frame rate).
- *Editor pacing*: vsync plus a cap at an even divisor of the refresh rate (72 on 144 Hz) instead of a fixed 60, which alternated two- and three-vblank frames.
- *GLib main context*: standalone games now dispatch it every frame (it was never iterated), so timeouts, async completions and the background save/analytics notifications run.

Tried and dropped: link-time optimisation across raylib, graylib and libregnum (=-flto=, fat objects) changed no scenario by more than noise (one +15% on =physics= work, everything else within 2%) and made the build about 2.5x slower.

** GPU skinning for animated glTF models
:PROPERTIES:
:CUSTOM_ID: gpu-skinning
:END:
=LrgModelAnimator= used to pose through raylib's =UpdateModelAnimation()=, which skins every vertex and normal on the CPU (a matrix inverse per influence for the normals) and re-uploads the position and normal buffers, once per actor per frame when actors are on different frames. It now poses the bones only and skins in the vertex shader whenever the materials allow it, with the CPU path as the fallback; see [[file:modules/graphics/model-animator.org::#skinning][GPU and CPU Skinning]] for the rules and the image comparison tests.

=lrg-bench= scenarios =skinned-models= (GPU, the default) and =skinned-models-cpu= (=set_gpu_skinning (FALSE)=, the code path every model took before): 50 actors on one 3880-vertex, 32-bone glTF tube, each on its own clip and frame, crossfading every two seconds. Xvfb + llvmpipe, =taskset -c 0-11=, 600 frames, three runs each (range):

| Scenario             | fps       | 1% low    | p99 frame      | work median    |
|----------------------+-----------+-----------+----------------+----------------|
| =skinned-models-cpu= | 46.5-47.8 | 36.2-38.7 | 25.2-25.8 ms   | 20.1-20.6 ms   |
| =skinned-models=     | 63.0-66.1 | 50.2-54.7 | 17.7-19.0 ms   | 14.0-14.8 ms   |

That is about +38 % fps and +40 % on the 1 % low on a software rasterizer, where the vertex shader itself runs on the CPU (llvmpipe's vertex stage is single threaded); on a hardware GPU the skinning is close to free. The shader skips zero weights: the first version summed four weighted matrices per vertex and was /slower/ than CPU skinning on llvmpipe (34.6 fps), because the dynamically indexed matrix fetches are gathers there.

** GPU-resource prewarm
:PROPERTIES:
:CUSTOM_ID: prewarm
:END:
The engine's renderers compiled their shaders and uploaded their buffers on their first draw, so a feature appearing mid-game (water coming into view, a post effect switching on, the first skinned actor) froze the frame it appeared on. The prewarm system (=LrgPrewarm=, =LrgPrewarmable=, the hidden draw; see [[file:modules/core/prewarm.org][Prewarm]]) moves that behind the loading screen: the renderers join a queue when created, =LrgTemplateLoadingState= runs it with a per-frame budget after its tasks, then emits =prewarm-draw= inside a hidden draw (empty scissor) for the game to draw its scene once, which makes the driver compile the shader variants it only compiles at a first draw.

=lrg-bench= scenarios =first-use= (nothing warmed), =first-use-queue= (the queue run in setup) and =first-use-prewarm= (the queue plus one hidden draw): water, 20000 billboards, ~40000 grass blades, a cloud layer, a lit static batch, 50 GPU-skinned actors, colour grade, heat haze and sharpen, all built in setup and first drawn at measured frame 100. Xvfb + llvmpipe, 600 frames, three runs each (range). "Cold" disables Mesa's on-disk shader cache (=MESA_SHADER_CACHE_DISABLE=true=, a first run or a driver update); "warm" leaves it on (the cache already holds these shaders):

| Scenario            | Cache | max frame       | 1% low    | p99 frame    |
|---------------------+-------+-----------------+-----------+--------------|
| =first-use=         | cold  | 867-960 ms      | 5.4-6.0   | 25.2-29.4 ms |
| =first-use-queue=   | cold  | 759-823 ms      | 6.2-6.6   | 29.1-30.5 ms |
| =first-use-prewarm= | cold  | 40-43 ms        | 24.7-31.5 | 28.4-39.8 ms |
| =first-use=         | warm  | 74-99 ms        | 21.9-26.4 | 27.7-38.9 ms |
| =first-use-queue=   | warm  | 51-70 ms        | 23.4-32.6 | 25.4-37.3 ms |
| =first-use-prewarm= | warm  | 34-48 ms        | 22.3-33.6 | 27.2-42.0 ms |

(The p99 is the steady frame of this heavy scene, ~20-25 ms on llvmpipe, and moved with machine load between runs; the max frame and the 1% low carry the hitch. With the full path the worst frame is under two steady frames.) In setup the queue cost 100-125 ms cold and 23-30 ms warm (9 entries), the hidden draw 746-883 ms cold and 30-39 ms warm: on llvmpipe =glLinkProgram()= does the front end only and the fragment code is generated at the first draw for its state, so most of the cold cost is only reachable by drawing. Parallel shader compilation (=GL_KHR_parallel_shader_compile=) was evaluated and left out for that reason; see [[file:modules/core/prewarm.org::#parallel-compile][the prewarm page]].

** The October 2026 hitch pass
:PROPERTIES:
:CUSTOM_ID: hitch-pass
:END:
Hitches are frames that cost far more than the median: they barely move the average but set the 1% / 5% lows and the jitter. Measured with =lrg-bench= under Xvfb + llvmpipe, =taskset -c 0-11=, 1000 frames, before (master =c49b031=) and after; each scenario reproduces one hitch.

| Scenario      | Before: fps, 1% low, p99            | After: fps, 1% low, p99            | What changed                                   |
|---------------+-------------------------------------+------------------------------------+------------------------------------------------|
| =autosave=    | 3545 fps, 1% low 104, p99 8.9 ms    | 6378 fps, 1% low 529, p99 1.6 ms   | file write (fsync) off the frame thread        |
| =analytics=   | 437 fps, 1% low 47, p99 21.2 ms     | 7302 fps, 1% low 694, p99 0.55 ms  | HTTP POST on a sender thread                   |
| =despawn=     | 417 fps, 1% low 174, p99 5.6 ms     | 436 fps, 1% low 232, p99 4.1 ms    | O(1) removal, sorted draw-order rebuild        |

(=autosave= before is the synchronous save; =autosave-sync= keeps measuring that path: 1% low ~100, p99 ~9 ms. The remaining =autosave= spike is collection, about 1.4 ms for 4000 keys through the YAML builder. The remaining =despawn= spike is creating 1000 objects with components.)

Fixed:
- *Save writes* (=src/save/lrg-save-manager.c=). A save replacing an existing file costs ~1.2 ms collecting, ~0.9 ms generating YAML and 6-9 ms in =g_file_set_contents()= (fsync), all on the frame. New =lrg_save_manager_save_in_background()= collects on the caller's thread and generates + writes on a per-manager writer thread, in order; =lrg_save_manager_flush()= waits and reports; synchronous save/load/delete wait for queued writes first. =lrg_save_manager_save()= is unchanged. See [[file:modules/save/index.org::#background-saves][Saving During Play]].
- *HTTP analytics* (=src/analytics/lrg-analytics-backend-http.c=). Every =batch-size= (10) events the backend POSTed synchronously from =lrg_analytics_track_event()=, with up to 3 retries 1 s apart when the collector was down: a 20 ms freeze per batch against a healthy collector, 3+ s against a dead one. Batches now go to a sender thread, one at a time; flush still blocks and reports. See [[file:modules/analytics/index.org::#http-sender-thread][the analytics page]].
- *Mass removal from a world* (=lrg_world_remove_object()=, graylib =grl_scene_remove_entity()=). Each removal walked the object list twice (=g_list_find= in the world and again in the scene), so removing k of n objects was O(k·n); both now keep the list link in their membership table. The draw order after any spawn or despawn was rebuilt with every z-index at 0 and insertion-sorted, O(n²) for mixed z-indices; it is now rebuilt with the real z-indices and sorted.
- *Per-frame large allocations*: the particle billboard renderer's sort list (52 B a particle, past 128 KiB at ~2500 particles), the billboard batch's draw and shadow-pass sort lists (8 B a candidate, once per shadow pass too) and the audio mixer's per-bus mix (64 KiB a bus per 4096-frame refill) and pump output are kept between frames instead of allocated per frame or refill.

Bugs fixed on the way (each has a regression test):
- =grl_scene_sort_entities_by_z()= left the scene's tail link stale, so the next =grl_scene_add_entity()= appended after a node that might not be last, or freed (graylib =/scene/remove-after-sort=).

Behaviour changes to know about:
- The standalone game loop now dispatches the default GLib main context every frame (bounded, non-blocking). Timeouts, idles, async completions and file monitors used to never run in standalone games; they now do, on the game thread, before the frame's update.
- =lrg_analytics_backend_send_event()= on the HTTP backend no longer sends a full batch itself and so no longer returns its network error; failures are logged from the sender thread and reported by =lrg_analytics_flush()=. Disposing of the backend drops batches not yet sent (it always dropped pending events); =lrg_analytics_end_session()= flushes first.

Looked at and fine: achievements (signals only, no I/O), settings (written at shutdown), template statistics and daily rewards (saveables only), the timer manager (no catch-up bursts, due timers sorted only), the event bus (no queued flush), net receive (non-blocking, bounded per poll), hot reload (=GFileMonitor=, no polling), logging (plain =g_log=; a dropped debug message costs ~0.1 µs), Lua (default incremental GC, no forced collections; the update hook does not allocate).

*** Known hitch sources not fixed
:PROPERTIES:
:CUSTOM_ID: known-hitches
:END:
- *Streamed synthesis in 4096-frame bursts.* =LrgMidiSynth=, =LrgSoundBed= and =LrgProceduralAudio= render a whole 4096-frame stream buffer (~85 ms of audio) on the frame the previous one is consumed, so about one frame in five pays it all (estimated 1.5-5 ms for a busy MIDI song, double while crossfading); after a long frame both buffers refill at once. Spreading the render over frames means rendering ahead of the stream, which delays live notes by up to a buffer; smaller stream buffers trade the burst for underrun risk. Left as is; a game that needs it can pump these from its own thread with a lock.
- *Music decoding.* raylib's =UpdateMusicStream()= decodes a whole sub-buffer per refill (4096 frames once a synth or sound bed set the default buffer size, else ~sample-rate/30 · 4 frames); 1-3 ms of Vorbis every few frames. raylib's, not changed.
- *First-use GPU work, when nothing prewarms.* The renderers still build lazily on their first draw (shaders of the light set, shadow casters, billboards, grass, water, clouds, ground overlay, GPU skinning, the post effects on their first non-identity frame; uploads of water patches, the horizon ring's batch, round shapes, skinned meshes, billboard GPU pages), so a game that neither runs the [[#prewarm][prewarm queue]] nor uses =LrgTemplateLoadingState= still hitches when a feature first appears, and anything *created* mid-game compiles when it is created and drawn (shaders are per instance; a renderer made during play is only warm if the game queues and runs it, e.g. behind a transition). Billboards added after the upload, and large later additions, rebuild the GPU pages on the second draw after they stop, as before. The driver's draw-time shader variants are only warmed by a real draw (the hidden draw).
- *Bursty game logic by design.* =LrgObjectPool= with =LRG_POOL_GROWTH_DOUBLE= constructs the whole growth step in one =acquire()= (prewarm the pool); =LrgWaveDirector= spawns every zero-interval entry in one frame and catches up after a long frame; =LrgAutomation= fires an interval rule once per missed interval after a stall; particle emitters keep their accumulated time while the pool is full and emit the backlog later.
- *Script hosts.* The GJS update hook evaluates generated JS twice per hook per frame, steady garbage that SpiderMonkey collects on its own schedule. LuaJIT count hooks do not fire inside compiled traces, so the scheduler's per-frame instruction budget is not enforced for hot compiled loops.
- *Networking.* =_lrg_net_buffer_flush()= shifts the whole remaining output queue (up to 4 MiB) after each partial write; the MMO SQLite store commits with =synchronous=FULL= and the Postgres store blocks on queries, which matters if a server shares a thread with its simulation tick.
