#+title: Audio mixer buses, sends, and effects

* Overview

=LrgAudioMixer= is an opt-in PCM playback and processing graph. It complements
=LrgAudioManager='s direct sound/music playback. Queue =LrgWaveData= through
=mixer_play= to use buses and effects; existing =GrlSound= instances playing
through the audio manager are not intercepted or rerouted.

A mixer has a fixed sample rate (8,000–192,000 Hz), one or two channels, and a
=master= bus. Construction, mixing, and effects work without a window or audio
device. A wave is copied and converted when queued, so its original object can
be freed or edited without changing the playing voice.

* Routing

Each named bus sends its processed output to its parent. Add post-fader sends
to other buses for parallel processing. The graph rejects cycles (including
cycles through parents), self-sends, sends from master, duplicate bus names,
and sends to a bus's existing parent. Gain zero removes a send. Buses can be
added in any dependency-safe order and sends can be edited between render calls.
Parents are fixed at bus creation; create a new mixer to replace the bus layout.

#+begin_src c
LrgAudioMixer *mixer = lrg_audio_mixer_new (48000, 2);

lrg_audio_mixer_add_bus (mixer, "sfx", "master");
lrg_audio_mixer_add_bus (mixer, "weapons", "sfx");
lrg_audio_mixer_add_bus (mixer, "echo", "master");
lrg_audio_mixer_set_bus (mixer, "sfx", 0.7, FALSE);
lrg_audio_mixer_set_effects (mixer, "echo", 5000.0, 0.15, 0.35, 1.0);
lrg_audio_mixer_set_send (mixer, "weapons", "echo", 0.2);

/* wave is an existing LrgWaveData, loaded or generated by the application. */
lrg_audio_mixer_play (mixer, wave, "weapons", 1.0, FALSE);
#+end_src

Signal flow within each bus is: summed voices/inputs → low-pass → feedback
delay → gain/mute → parent and sends. The one-pole low-pass maintains separate
history for each channel. Delay supports up to two seconds, feedback in [0,1),
and wet blend in [0,1]. Zero cutoff or zero delay bypasses the corresponding
effect. A successful effect edit resets its history; invalid edits preserve it.
Bus/voice/send gain must be finite and between zero and four. Master output is
clipped to [-1,1]; intermediate buses retain headroom.

Mute silences bus output and sends while advancing voices and effect histories.
Voice pause freezes only that voice's cursor. Stopping a voice does not erase
effect tails. Completed non-looping voices are removed after the last sample;
voice IDs are never reused by the mixer. Effect tails continue with no active
voices, so a zero voice count does not mean that rendered output is silent.

* Offline rendering

#+begin_src c
gsize n_samples = 0;
g_autofree gfloat *pcm = lrg_audio_mixer_render (mixer, 1024, &n_samples);
g_autoptr(LrgWaveData) output = NULL;

output = lrg_wave_data_new_from_samples (48000, 32, 2,
                                        (const guint8 *)pcm,
                                        n_samples * sizeof (gfloat));
lrg_wave_data_export_wav (output, "mixed.wav", &error);
#+end_src

Each render accepts 1–65,536 frames and advances the graph by exactly those
frames. Frame boundaries do not reset effects or looping voices. The API counts
interleaved *samples* in the result, so stereo has twice as many samples as frames.

* Live stream integration

Initialize the audio device using the normal graylib lifecycle. Create and play
a matching 32-bit =GrlAudioStream=, then call =lrg_audio_mixer_pump= from the game
loop. The pump does nothing while stopped/paused or while the stream needs no
refill. Format mismatches return =G_IO_ERROR_INVALID_ARGUMENT= without advancing
the graph. The caller owns the device and stream and must choose a block size
that fits the configured stream buffer.

#+begin_src c
/* After obtaining a ready GrlAudioDevice: */
g_autoptr(GrlAudioStream) stream = NULL;

grl_audio_stream_set_default_buffer_size (2048);
stream = grl_audio_stream_new (48000, 32, 2);
if (stream != NULL && grl_audio_stream_is_valid (stream))
{
    grl_audio_stream_play (stream);
    /* Once per host frame while playing: */
    lrg_audio_mixer_pump (mixer, stream, 2048, &error);
}
#+end_src

All graph edits, voice operations, rendering, and pumping must use one thread.
Rendering allocates scratch storage and is intended for main-thread stream
refills or offline export, not an audio-device callback with real-time allocation
constraints. There are at most 256 buses, including master. Queueing performs
conversion up front; repeated render calls do not resample sources. Releasing
the mixer frees all voices and effect buffers. It does not own the output stream.

* Tests

=tests/test-audio-mixer.c= covers nested routing, parallel sends, graph-cycle
rejection, independent sample ownership, pause/loop/stop, mute advancement,
channel isolation, delay tails across blocks, low-pass continuity, channel
conversion, clipping, and invalid edits. These sample-level tests are headless;
actual device playback requires an audio device.

Run =make test-followups-gi= to exercise mixer sample ownership through Python
GI as well. Set =GI_PYTHON= if the system interpreter lacks PyGObject.
