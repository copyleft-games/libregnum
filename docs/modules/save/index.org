* Save Module
:PROPERTIES:
:CUSTOM_ID: save-module
:END:
The Save module provides a complete save/load system with support for multiple save slots, asynchronous operations, and custom object serialization. Games implement the =LrgSaveable= interface to participate in saves.

** Overview
:PROPERTIES:
:CUSTOM_ID: overview
:END:
The Save module consists of five core classes:

- *LrgSaveManager* - Singleton manager coordinating all save/load operations
- *LrgSaveGame* - Metadata for a single save slot
- *LrgSaveContext* - Serialization context for reading/writing YAML data
- *LrgSaveable* - Interface for objects that can be saved/loaded
- *LrgSaveDocument* / *LrgSaveMigrator* - Saved data as a document and its chained conversion from older versions ([[file:migrator.org][migrator]])
- Save slots tracked by name (e.g., "slot1", "autosave")

** Key Features
:PROPERTIES:
:CUSTOM_ID: key-features
:END:
- *Multiple save slots* - Support multiple named save files
- *Saveable interface* - Objects opt-in to serialization
- *Context-based serialization* - YAML format for human-readable saves
- *Asynchronous saves* - Non-blocking save/load with libdex futures
- *Version tracking* - Track save format version for compatibility
- *Chained conversion* - =LrgSaveMigrator= converts data of any older format and section version step by step, atomically
- *Metadata storage* - Timestamp, playtime, custom data per save
- *Section management* - Organize data by saveable object ID
- *Signal notifications* - Events for save/load start and completion

** Quick Start
:PROPERTIES:
:CUSTOM_ID: quick-start
:END:
#+begin_src C
/* Implement LrgSaveable interface */
struct _MyGameState {
    GObject parent;
    gint gold;
    gint level;
    gchar *player_name;
};

static const gchar *
my_game_state_get_save_id(LrgSaveable *self) {
    return "game_state";
}

static gboolean
my_game_state_save(LrgSaveable *self, LrgSaveContext *ctx, GError **error) {
    MyGameState *state = MY_GAME_STATE(self);
    lrg_save_context_begin_section(ctx, "game_state");
    lrg_save_context_write_int(ctx, "gold", state->gold);
    lrg_save_context_write_int(ctx, "level", state->level);
    lrg_save_context_write_string(ctx, "player_name", state->player_name);
    lrg_save_context_end_section(ctx);
    return TRUE;
}

static gboolean
my_game_state_load(LrgSaveable *self, LrgSaveContext *ctx, GError **error) {
    MyGameState *state = MY_GAME_STATE(self);
    if (!lrg_save_context_enter_section(ctx, "game_state")) {
        return FALSE;
    }
    state->gold = lrg_save_context_read_int(ctx, "gold", 0);
    state->level = lrg_save_context_read_int(ctx, "level", 1);
    g_free(state->player_name);
    state->player_name = g_strdup(
        lrg_save_context_read_string(ctx, "player_name", "Hero")
    );
    lrg_save_context_leave_section(ctx);
    return TRUE;
}

/* Use the save system */
LrgSaveManager *manager = lrg_save_manager_get_default();
lrg_save_manager_set_save_directory(manager, "~/.local/share/mygame/saves");

/* Register objects */
lrg_save_manager_register(manager, LRG_SAVEABLE(game_state));
lrg_save_manager_register(manager, LRG_SAVEABLE(player_inventory));
lrg_save_manager_register(manager, LRG_SAVEABLE(quest_log));

/* Save to a slot */
if (lrg_save_manager_save(manager, "slot1", NULL)) {
    g_print("Game saved\n");
}

/* Load from a slot */
if (lrg_save_manager_load(manager, "slot1", NULL)) {
    g_print("Game loaded\n");
}
#+end_src

** Asynchronous Operations
:PROPERTIES:
:CUSTOM_ID: asynchronous-operations
:END:
For non-blocking save/load:

#+begin_src C
/* Save asynchronously */
DexFuture *future = lrg_save_manager_save_async(manager, "slot1");
dex_future_then(future, on_save_complete, NULL, NULL);

/* Load asynchronously */
DexFuture *future = lrg_save_manager_load_async(manager, "slot1");
dex_future_then(future, on_load_complete, NULL, NULL);
#+end_src

** Saving During Play (Background Saves)
:PROPERTIES:
:CUSTOM_ID: background-saves
:END:
=lrg_save_manager_save()= does the whole save on the calling thread: every saveable's =save= method, YAML generation and the file write. Replacing an existing save fsyncs (=g_file_set_contents()=), which costs several milliseconds on a laptop SSD and far more on a busy or spinning disk; with a 4000-key state the whole save took about 9 ms, a visible hitch when an autosave fires mid-game.

=lrg_save_manager_save_in_background()= splits it. The saveables still run on the calling thread (they read live game state, which only that thread may touch), but the YAML generation and the file write run on the manager's writer thread. Background saves are written one at a time in the order they were made, and a later synchronous save, load or delete of any slot first waits for them, so a save never lands on top of a newer one and a load never reads a half-written slot.

#+begin_src C
static gboolean
my_game_on_auto_save (LrgGameTemplate  *template,
                      GError          **error)
{
    /* Collects now (about 1.4 ms for 4000 keys), writes on the writer thread */
    return lrg_save_manager_save_in_background (lrg_save_manager_get_default (),
                                                "autosave", "Autosave", error);
}

/* Before quitting (or when the result matters): wait for the writes */
if (!lrg_save_manager_flush (lrg_save_manager_get_default (), &error))
    g_warning ("Last save failed: %s", error->message);
#+end_src

Reporting:
- =save-started= is emitted at once; =save-completed= when the file is written. It is emitted on the thread that saved: from the thread-default main context current at the first background save when that context is iterated (the editor, a =GMainLoop= app), and otherwise from the next =lrg_save_manager_flush()= or synchronous save, load or delete. The standalone game loop does not iterate a main context, so there completions arrive at those calls.
- The return value covers collection only (a saveable that fails means nothing is written). Write errors come through =save-completed= (=success= FALSE), a warning in the log, and =lrg_save_manager_flush()=, which returns the first write error since the previous flush.
- =lrg_save_manager_is_saving()= is TRUE while a background save is queued or being written, e.g. to show a save icon.
- Disposing of the manager finishes its queued writes first.

** YAML Format
:PROPERTIES:
:CUSTOM_ID: yaml-format
:END:
Saves are stored as YAML with sections for each saveable object:

#+begin_src yaml
version: 1
game_state:
  gold: 1000
  level: 15
  player_name: Hero
inventory:
  items:
    - id: sword
      count: 1
    - id: potion
      count: 5
quest_log:
  active_quests:
    - slay_dragon
    - collect_herbs
  completed_quests:
    - forest_bridge
#+end_src

** Save format compatibility

Set =LrgSaveManager:save-version= to the positive format version written and
understood by the game. Before invoking any registered saveable's load method,
the manager rejects a newer version with =LRG_SAVE_ERROR_VERSION_MISMATCH=.
It emits =load-completed= with failure after =load-started=, leaves gameplay
objects untouched, and does not rewrite the save file. Async loads use the
same check through the synchronous implementation.

Current and older positive versions remain loadable. Saveables can inspect
=lrg_save_context_get_version()= to apply their own field migrations. This
check does not supply game-specific migrations or roll back changes made by a
saveable whose own load method later fails.  For game-specific conversions
that must be atomic and may span several versions at once, read the file into
an =LrgSaveDocument= and convert it with =LrgSaveMigrator=
([[file:migrator.org][migrator]]) before applying anything.

A missing version field identifies a legacy version-1 save. A present field
must be a positive decimal integer no larger than =G_MAXUINT=. Quoted decimal
digits are accepted; signs, whitespace, floating point, booleans, null,
collections, zero, and overflow fail with =LRG_SAVE_ERROR_CORRUPT=. Writers
and version setters require versions of at least 1. Metadata inspection can
still read structurally valid newer saves using =LrgSaveContext= directly;
compatibility enforcement belongs to the manager that applies gameplay state.

Tests cover malformed headers, the maximum version, legacy defaults,
future-version rejection without state/file changes, and loading equal/older
versions.
