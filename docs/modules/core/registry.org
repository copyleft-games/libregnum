** Overview
:PROPERTIES:
:CUSTOM_ID: overview
:END:
LrgRegistry enables fully data-driven gameplay by mapping readable type names to GTypes:

#+begin_src C
lrg_registry_register (registry, "player", MY_TYPE_PLAYER);
GObject *player = lrg_registry_create (registry, "player", NULL);
#+end_src

See [[../../concepts/type-registry.md][Type Registry Concept]] for detailed information.

** Example
:PROPERTIES:
:CUSTOM_ID: example
:END:
#+begin_src C
#include <libregnum.h>

int main ()
{
    LrgRegistry *registry = lrg_registry_new ();

    /* Register types */
    lrg_registry_register (registry, "player", MY_TYPE_PLAYER);

    /* Create by name */
    GObject *obj = lrg_registry_create (registry, "player",
                                        "name", "Hero",
                                        NULL);

    g_object_unref (obj);
    g_object_unref (registry);
    return 0;
}
#+end_src

** Registry names in composite documents
:PROPERTIES:
:CUSTOM_ID: registry-composite
:END:
Composite documents ([[file:data-loader.org::#composite-documents][LrgDataLoader composite documents]]) use the registry in both directions: =type: name= in a document is looked up with =lrg_registry_lookup()= (the type must be an instantiable =GObject= type that fits the slot), and the writer names an object's type with =lrg_registry_lookup_name()= (the smallest name when a type has several, so register one canonical name per type, plus aliases that sort after it). A type written with =type:= must be registered, or =lrg_data_loader_save_to_data()= fails with =LRG_DATA_LOADER_ERROR_TYPE=. Types only ever used in slots that imply them (a concrete object property, a container's default child type, the root type a format passes) need no name. See [[file:../../guides/writing-a-data-format.org][Writing a data format]].

** Built-in type catalog
:PROPERTIES:
:CUSTOM_ID: built-in-type-catalog
:END:
Engine startup calls =lrg_registry_register_builtin()= before connecting its data loader, so YAML definitions (=type: rigid-body=), the asset manager, the scripting registries and MCP spawning (=lrg_ecs_spawn_object=) resolve the engine's own types without any application registration. The catalog is a static, data-driven table (=builtin_catalog= in =src/core/lrg-registry.c=) of name and =get_type= function pairs; installing it only creates mappings, it instantiates nothing.

*** Naming
:PROPERTIES:
:CUSTOM_ID: built-in-naming
:END:
Names are kebab-case: the type's C prefix without =lrg_= (=lrg_point_light2d= becomes =point-light2d=, =lrg_item_def= becomes =item-def=). ECS components drop the =-component= suffix (=transform=, not =transform-component=), and so do the 3D components of =LrgWorld3D= (=mesh-renderer=, =light=, =reflection-probe=; since 0.9.0). The 3D physics components (0.9.0 M5) take a =3d= suffix because the plain names belong to the 2D physics: =rigid-body3d= (#LrgRigidBodyComponent; =rigid-body= is the 2D #LrgRigidBody), =collider3d= (#LrgColliderComponent3D; =collider= is the ECS #LrgColliderComponent) and =joint3d= (#LrgJointComponent). The 3D names are short because they live in the same namespace as everything else: =light= is #LrgLightComponent, while the 2D lights keep their =point-light2d= style names. These are the same names applications already used when they registered engine types by hand.

Only =game-object= (and application subclasses) can be spawned with =lrg_ecs_spawn_object=; the other names serve YAML definitions, scripting and the editor's component list (components only).

*** What is left out
:PROPERTIES:
:CUSTOM_ID: built-in-exclusions
:END:
- Abstract bases (=LrgComponent=, =LrgShape=, =LrgTrigger2D=, =LrgLight2D=, =LrgBTNode=...).
- Device and GPU resources (windows, textures, render targets, audio devices, shadow maps, light probes) and singletons (engine, managers with =get_default()=).
- =LrgScriptComponent=: scripts attach through script bindings; a bare script component would only clutter the editor's component list.
- Boxed value types (=LrgSpawnPoint3D=, =LrgTrigger3D=, =LrgPortal=...), which the registry cannot instantiate.
- Module-specific catalogs registered by their own loaders, such as the reel clip types (=solid-clip=, =text-clip=...) that =LrgReelLoader= installs.

*** Overrides and idempotence
:PROPERTIES:
:CUSTOM_ID: built-in-overrides
:END:
A standalone registry starts empty; call =lrg_registry_register_builtin()= to populate it. The call only fills names that are not registered yet, so it never replaces an application or mod mapping (an application registering its own =game-object= subclass under =game-object= keeps it), and calling it again adds nothing. =clear()= removes both built-in and custom registrations; a later =register_builtin()= restores the engine mappings. Adding a type to the catalog: append a row to =builtin_catalog= (it must pass the headless construction test) and to the table above.

For example, after engine startup its data loader can load:

#+begin_src yaml
type: game-object
x: 42
#+end_src

Multiple names may refer to one type. Reverse lookup returns the
lexicographically smallest registered name in byte order, independent of hash
iteration order. Replacing or removing one alias preserves the others. Returned
names are borrowed; copy them to retain them across mutations. Passing a borrowed
name directly to =register()= or =unregister()= is supported. Reverse lookup scans
the registry; forward lookup remains a hash lookup. Registry access requires
external synchronization if shared between threads.
