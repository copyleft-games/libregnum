* LrgResetSchedule - Daily and Weekly Resets
:PROPERTIES:
:CUSTOM_ID: lrgresetschedule---daily-and-weekly-resets
:END:
Pure, deterministic arithmetic for "daily reset at 04:00" and "weekly reset on Tuesday" style periods, used by repeatable quests (=LrgQuestLog=) and any other content with daily or weekly caps. The schedule never reads the clock: every query takes Unix seconds supplied by the caller (on an MMO server, the trusted server time), so results are reproducible and testable. The UTC offset is fixed; there are no daylight saving rules.

** Type
:PROPERTIES:
:CUSTOM_ID: type
:END:
- *Final GObject Class* - Cannot be subclassed
- *Type ID* - =LRG_TYPE_RESET_SCHEDULE=
- *GIR Name* - =Libregnum.ResetSchedule=

** Properties
:PROPERTIES:
:CUSTOM_ID: properties
:END:
| Property | Type | Range | Default | Meaning |
|----------+------+-------+---------+---------|
| =reset-hour= | =guint= | 0-23 | 0 | Local hour of the reset |
| =reset-minute= | =guint= | 0-59 | 0 | Local minute of the reset |
| =weekly-day= | =guint= | 1-7 | 2 (Tuesday) | =GDateWeekday= of the weekly reset (1 = Monday, 7 = Sunday) |
| =utc-offset= | =gint= | -720 to 840 | 0 | Offset of the reset clock from UTC in minutes |

Setters reject out-of-range values with =g_return_if_fail()= (a programmer error that leaves the schedule unchanged) and notify only when the value changes.

** Period Semantics
:PROPERTIES:
:CUSTOM_ID: period-semantics
:END:
A reset boundary is an instant at which the local clock (UTC plus =utc-offset=) reads =reset-hour:reset-minute:00=; for weekly periods the local day must also be =weekly-day=. Period N is the half-open interval =[start(N), start(N+1))=, with =start(N+1) - start(N)= equal to 86400 (daily) or 604800 (weekly).

- *Index 0* is the period that begins at the first boundary at or after the Unix epoch, so times before that boundary have negative indices.
- *Floor division* is used throughout: times before 1970 behave exactly like later times, and consecutive periods always differ by one.
- *At the reset instant* =lrg_reset_schedule_get_period()= already returns the new period and =lrg_reset_schedule_get_next_reset()= returns the following boundary (one full period later); one second earlier belongs to the old period.
- *Overflow*: all queries are safe over the whole =gint64= range. Period starts that cannot be represented saturate at =G_MININT64= / =G_MAXINT64=.

** MMO Usage
:PROPERTIES:
:CUSTOM_ID: mmo-usage
:END:
Create one schedule per realm at server start and share it with every quest log check. Store the schedule's configuration with the realm configuration rather than per character: completion records only store Unix seconds, so changing the reset hour later re-buckets old completions consistently. Clients may be sent =lrg_reset_schedule_get_seconds_until_reset()= for countdown timers, but eligibility is always decided on the server.

** Example
:PROPERTIES:
:CUSTOM_ID: example
:END:
#+begin_src C
/* Resets at 03:00 in UTC-05:00 (08:00 UTC); weekly on Tuesday. */
g_autoptr(LrgResetSchedule) schedule = lrg_reset_schedule_new (3, G_DATE_TUESDAY, -300);
gint64 now = trusted_server_time ();

gint64 today = lrg_reset_schedule_get_period (schedule, LRG_RESET_PERIOD_DAILY, now);
gint64 last  = lrg_reset_schedule_get_period (schedule, LRG_RESET_PERIOD_DAILY, last_bonus_claim);
if (last < today)
    grant_daily_login_bonus (character);

g_print ("Weekly reset in %" G_GINT64_FORMAT " seconds\n",
         lrg_reset_schedule_get_seconds_until_reset (schedule, LRG_RESET_PERIOD_WEEKLY, now));
#+end_src
