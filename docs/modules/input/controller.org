* Controllers
:PROPERTIES:
:CUSTOM_ID: controllers
:END:
=lrg-controller.h= and =lrg-controller-rumble.h= tell a game which kind of pad is in the player's hands, so it can show the right button names, offer the right preset map and vibrate it. They extend the existing =LrgInputGamepad= (which keeps the coarse =LrgGamepadType=); nothing here replaces it.

** Overview
:PROPERTIES:
:CUSTOM_ID: overview
:END:
- =LrgControllerFamily= (registered enum, stable nicks): =unknown= (nothing connected), =generic=, =xbox-360=, =xbox-one=, =xbox-series=, =dualshock4=, =dualsense=, =dualsense-edge=, =switch-pro=, =steam-controller=, =steam-deck=, =steam-frame=.
- =lrg_controller_family_detect()= is a pure function of the controller name, the USB vendor/product ids and a "this is a Steam Deck" flag.
- =LrgControllerMonitor= watches one gamepad slot of any =LrgInput= (the real gamepad source or an =LrgInputMock=) and emits =family-changed(old, new)= when a pad connects, is swapped or removed.
- Glyph names: =lrg_controller_get_glyph()= / =lrg_controller_get_button_glyph()= / =lrg_controller_get_axis_glyph()= (A/B/X/Y against Cross/Circle/Square/Triangle, the Deck's L4 R4 L5 R5 and "QAM", the Frame's grips, the DualSense Edge's paddles).
- Preset input maps: =lrg_controller_preset_lookup()= (role to button or stick direction) and =lrg_controller_preset_new_map()= (an =LrgInputMap=, one action per role).
- =LrgControllerRumble=: vibration through Linux force feedback.

** Detection
:PROPERTIES:
:CUSTOM_ID: detection
:END:
The order is ids, then name, then the Steam Deck rule:

1. The ids (=lrg_input_get_gamepad_ids()=). The real gamepad source has no ids from raylib, so it reads them from Linux sysfs: =lrg_controller_probe_usb_ids()= finds =class/input/input*= whose =name= equals the name raylib reports and reads =id/vendor= and =id/product=. This works for USB, Bluetooth and Steam Input pads whatever index GLFW gave them. Other systems fall through to the name.
2. The name (case-insensitive substrings, most specific first). The bare "Wireless Controller" the Linux kernel names a DualShock 4 is a DualShock 4 only after every Xbox name was ruled out ("Xbox Wireless Controller" is an Xbox One pad).
3. On a Steam Deck or a Steam Frame host, a pad that is only the Xbox 360 shaped virtual pad Steam Input presents (or one nothing matched) is =steam-deck=: those are the Deck's own controls (=steam-frame= on a Frame: the Frame's two controllers). A pad that names itself as something else keeps its family. =lrg_controller_host_family()= says which host this is, and =lrg_controller_family_detect_on_host()= takes it (=lrg_controller_family_detect()= is the same with a Deck flag).
   - Deck: =SteamDeck=1= in the environment (Steam sets it for games on the Deck) or the DMI product name =Jupiter= / =Galileo= with board vendor =Valve= (=lrg_controller_is_steam_deck_host()=).
   - Frame: =ID=steamos= with =VARIANT_ID=vr= in =/etc/os-release= or =/usr/lib/os-release=, or in the host's copies under =/run/host= so a game in a distrobox or toolbox on the Frame knows it too (=lrg_controller_is_steam_frame_host()=). The Frame is an arm64 machine with no DMI. It is checked before the Deck, since Steam may set =SteamDeck=1= on the Frame as well.

GLFW, and so raylib, takes any input device with keys and absolute axes for a joystick. On a Steam Frame the ambient light sensor (=als31300=) and a Bluetooth keyboard with an axis are slots 0 and 1 ahead of Steam Input's pad, so a game that uses the first slot reads a sensor. =lrg_controller_probe_is_gamepad()= reads the device's =capabilities/key= from sysfs and says whether it has any joystick or gamepad button (=BTN_JOYSTICK= 0x120 to =BTN_THUMBR= 0x13e); a game skips the slots it rejects. The key bitmap is printed as long words, most significant first, so bit /n/ is bit /n/ mod 64 of the word /n/ / 64 counted from the end. A device with several nodes of one name (a pad and its motion sensors) is a pad when any of them has the buttons; a name sysfs does not know is taken as a pad.

The environment variable =LRG_CONTROLLER_FAMILY= (a nick) forces the family of every monitor created afterwards; =lrg_controller_monitor_set_family_override()= does it for one monitor (a "my controller is..." menu item).

*** Steam Frame
:PROPERTIES:
:CUSTOM_ID: steam-frame
:END:
Checked on a Steam Frame (SteamOS, =VARIANT_ID="vr"=, =VERSION_ID=0.4.5=, October 2026). The Frame's two controllers are not HID pads a game can open: they pair with the headset and reach SteamVR, which hands them to Steam as one virtual device, "Steam Frame Controllers" (28de:11e0, =/steamvr/virtual=). Steam Input then gives a game the usual uinput pad, "Microsoft X-Box 360 pad 0" (28de:11ff), which GLFW maps as "Steam Virtual Gamepad". What the game sees in =/dev/input= on the Frame:
| Slot | Device | Ids | A pad? |
|------+--------+-----+--------|
| 0 | =als31300= (ambient light sensor) | 0000:0000 | no: no keys |
| 1 | a Bluetooth keyboard, if paired (here an MX Keys Mini) | 046d:b369 | no: no joystick or gamepad buttons |
| 2 | =Microsoft X-Box 360 pad 0= | 28de:11ff | yes |
So a game must skip non-pads (=lrg_controller_probe_is_gamepad()=) and name the virtual pad after the host (=steam-frame=). The upstream lists (Linux =hid-ids.h= / =hid-steam.c=, SDL, Valve's =steam-devices= rules) still have no pad id for the Frame; 28de:11e0 is matched because the device does show up under that id when a process sees SteamVR's devices directly. An unknown Valve product id without a Frame name is still =generic=, never guessed.

Steam Input decides what the virtual pad sends from the focused app's controller configuration. A program started from a terminal or the desktop (not as a Steam game) gets the desktop configuration, which maps the controllers to mouse and keyboard and leaves the pad silent; add the game to Steam as a non-Steam game (=steamos-add-to-steam=) or pick a gamepad template for it. The glyph labels for the Frame follow the Deck's L1/L2/R1/R2 and call the grips "Left Grip" and "Right Grip".

** Glyphs
:PROPERTIES:
:CUSTOM_ID: glyphs
:END:
Raylib/GLFW only report the standard 17 buttons (=GrlGamepadButton=); the first 18 values of =LrgControllerControl= equal them. The rest (back paddles, touchpad, quick access) are glyph-only: they reach a game only when Steam Input or the OS driver maps them to a standard button. =lrg_controller_has_control()= says whether a family has a control, and =lrg_controller_get_glyph()= returns =NULL= for one it lacks. Unknown and generic pads use the Xbox One labels, matching the SDL mapping raylib applies.

** Presets
:PROPERTIES:
:CUSTOM_ID: presets
:END:
Roles: =move-up/down/left/right= (left stick), =look-up/down/left/right= (right stick), =confirm=, =cancel= (the family's own), =face-south=, =face-east=, =face-west=, =face-north= (by position, never swapped), =page-previous= (left bumper), =page-next= (right bumper), =trigger-left=, =trigger-right=, =view=, =menu=, =guide=, =stick-left-click=, =stick-right-click= and the four =dpad-*=. The families share the physical layout except the Switch Pro, whose =confirm= is the right face button (its A) and =cancel= the bottom one (its B). A game maps its own actions onto roles (librefall's preset does, see its controls manual).

** Monitor example
:PROPERTIES:
:CUSTOM_ID: monitor-example
:END:
#+begin_src C
static void
on_family_changed(
    LrgControllerMonitor *monitor,
    LrgControllerFamily   old_family,
    LrgControllerFamily   new_family,
    gpointer              user_data
){
    g_message("controller: %s", lrg_controller_family_get_display_name(new_family));
}

monitor = lrg_controller_monitor_new(input, 0);
g_signal_connect(monitor, "family-changed", G_CALLBACK(on_family_changed), NULL);

/* once per frame */
lrg_controller_monitor_poll(monitor);
#+end_src

With an =LrgInputMock= a test sets the pad with =lrg_input_mock_set_gamepad_available()=, =lrg_input_mock_set_gamepad_name()= and =lrg_input_mock_set_gamepad_ids()=.

** Rumble
:PROPERTIES:
:CUSTOM_ID: rumble
:END:
Raylib and GLFW have no rumble API. =LrgControllerRumble= finds the pad's input device by name under =class/input=, opens =/dev/input/eventN= and uploads an =FF_RUMBLE= effect (=lrg_controller_rumble_play(strong, weak, ms)=). Everything fails soft with a =GError= (no device, no permission, no rumble support, not Linux), and a failed open is remembered so a game does not retry on every hit. It does not reach pads Steam Input owns (a Deck or Frame in Steam's game mode) or Bluetooth pads whose kernel driver lacks force feedback. The tests cover the failure paths with fake sysfs and device trees; no pad with force feedback is attached to the test machine.

** Tests
:PROPERTIES:
:CUSTOM_ID: tests
:END:
=tests/test-controller.c= covers detection by name and ids, the sysfs probe against a fake tree, Deck and Frame host detection (fake DMI and os-release trees, including =/run/host=), the gamepad check against fake =capabilities/key= files shaped like the Frame's, glyph tables, preset lookup and maps driven through =LrgInputMock=, the monitor's connect/swap/remove signals, the environment override and the rumble failure paths.
