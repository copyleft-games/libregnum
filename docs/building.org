* Building Libregnum
:PROPERTIES:
:CUSTOM_ID: building-libregnum
:END:
This guide explains how to build Libregnum from source.

The oldest toolchain it must build on is Ubuntu 24.04 (GLib 2.80, GCC 13): librewow's AppImage is built there, and warnings are errors. GCC 13 rejects =alloca= and =g_newa()= under =-Wstack-protector=. Do not use GLib API newer than 2.80 (=g_sort_array()= is 2.82; use =qsort()=) unless it is behind =GLIB_CHECK_VERSION=. Ubuntu installs =gio/gunix*.h= in a separate directory, so code including them needs =pkg-config --cflags gio-unix-2.0=.

*** Build Targets
:PROPERTIES:
:CUSTOM_ID: build-targets
:END:
| Target           | Description                     |
|------------------+---------------------------------|
| =make=           | Build library (default)         |
| =make lib=       | Build library only              |
| =make gir=       | Generate GIR files              |
| =make test=      | Build and run tests             |
| =make test-sanitize= | Run tests under ASan+UBSan (own build dir) |
| =make test-valgrind= | Run tests under valgrind (excludes scripting tests) |
| =make examples=  | Build examples                  |
| =make docs=      | Build documentation             |
| =make install=   | Install to PREFIX               |
| =make clean=     | Clean build artifacts (cross targets' directories are kept) |
| =make clean-targets= | Clean every cross target's build directories |
| =make distclean= | Clean everything including deps |
| =make test-build-system= | Build-system tests plus the native no-regression gate |
| =make test-minimal-features= | Build without libsoup and libpq (=build/minimal=) and test the stubs |
| =make test-cross-arm64= / =-windows= / =-android= | One cross target's whole gate: build, tests, examples, binary checks |
| =make test-cross= | The three =test-cross-*= gates, one after another |
| =make ANDROID=1 test-device APK_GAME=...= | Run the game's APK on an adb device or emulator (skips without one) |
| =make test-native-unchanged= | Prove =make -Bn= output matches =BASE= (default: merge-base with master) and the stored baseline (on its host) |
| =make update-native-golden= | Record =BASE='s native commands in =tests/golden/native-make-n/= for this host |
| =make print-target= | Show the target, build directory and toolchain these switches select |
| =make targets=   | List every build target and its directories |
| =make help=      | Show all targets                |

Every goal takes a target switch (=WINDOWS=1=, =ARM64=1=, =ANDROID=1= or =LRG_TARGET=<target>=) to build for another platform into its own directory; see [[#cross-compilation][Cross-Compilation]].

*** Debug Options
:PROPERTIES:
:CUSTOM_ID: debug-options
:END:
#+begin_src makefile
DEBUG := 0             # Set to 1 for debug build
ENABLE_TRACE := 0      # Set to 1 for trace logging
SANITIZE := 0          # Set to 1 for ASan+UBSan build (implies DEBUG=1;
                       # builds into build/sanitize/ so it cannot collide
                       # with a normal debug build)
MINIMAL_FEATURES := 0  # Set to 1 to leave every optional dependency out
                       # (SOUP=0 LIBPQ=0) into build/minimal/; native only
                       # (make test-minimal-features)
ASAN := 0              # AddressSanitizer (requires DEBUG=1)
UBSAN := 0             # UndefinedBehaviorSanitizer (requires DEBUG=1)
#+end_src

*** Target Options
:PROPERTIES:
:CUSTOM_ID: target-options
:END:
#+begin_src makefile
LRG_TARGET := <host>   # windows-amd64, linux-arm64, android-arm64
WINDOWS := 0           # 1 = LRG_TARGET=windows-amd64
ARM64 := 0             # 1 = LRG_TARGET=linux-arm64
ANDROID := 0           # 1 = LRG_TARGET=android-arm64
#+end_src

These belong on the command line, not in =config.mk=. A cross target builds into =build/<release|debug>-<target>=; the native build keeps =build/release= and =build/debug=. Details: [[file:cross-compile.org][Cross-Compilation Guide]].

*** Testing & Memory Checking
:PROPERTIES:
:CUSTOM_ID: testing-memory-checking
:END:

Beyond =make test=, two targets verify memory correctness across the test
suite. Both set =G_SLICE=always-malloc= and =G_DEBUG=gc-friendly= at runtime
so GLib's slice allocator does not hide individual allocations from the tools
(=g_slice_*= is used across the codebase).

**** =make test-sanitize=

Builds the library and tests into an isolated =build/sanitize/= directory
with =-fsanitize=address,undefined= (=SANITIZE=1= implies =DEBUG=1=,
=ASAN=1=, =UBSAN=1=), runs the full suite with =detect_leaks=1=, and reports
any ASan/UBSan finding. Because the output directory is separate, no prior
=make clean= is needed and a normal =make test= run is unaffected.

#+begin_src sh
make test-sanitize
#+end_src

Confirmed-benign leaks (process-lifetime singletons such as
=LrgCrashReporter=) are filtered via [[file:../tests/lsan.supp][tests/lsan.supp]],
wired through =LSAN_OPTIONS=suppressions==. Leak suppressions go in
=LSAN_OPTIONS= (the =leak:<regex>= format), *not* =ASAN_OPTIONS= -- ASan's
=suppressions== accepts only interceptor types and rejects =leak:=. The
=test-scripting*= binaries are excluded from the sanitize run by default
(see =SANITIZE_BINARIES= in =tests/Makefile=) for the same reason as valgrind.

**** =make test-valgrind=

Builds a plain (non-instrumented) =DEBUG=1= build and runs the suite under
=valgrind --leak-check=full= with the starter suppressions file
[[file:../tests/valgrind.supp][tests/valgrind.supp]]. ASan and valgrind
conflict, so this target does *not* use sanitizers.

#+begin_src sh
make test-valgrind
#+end_src

The five =test-scripting*= binaries are excluded from the valgrind run by
default (see =VALGRIND_BINARIES= in =tests/Makefile=) because they =dlopen=
CPython/GJS, whose runtimes emit large benign leak footprints. Override with
=VALGRIND_TESTS=...= to run a custom set.

Any ASan/UBSan report or valgrind "definite leak" is a *real* defect to file,
not a tooling artifact. Only add a suppression to =tests/valgrind.supp= once
the leak is confirmed to be benign library/tool noise; the starter file is
expected to grow as real runs surface noise.

*** Tests never touch the desktop
:PROPERTIES:
:CUSTOM_ID: testing-desktop-guard
:END:
Every test binary links =tests/lrg-test-guard.c=. Its constructor runs before =main()= and sets =LRG_EXTERNAL_EDITOR=none=, so no test opens =$VISUAL= or the desktop default application, whether the binary is run by =make test= or by hand. A new test needs nothing for this: =tests/Makefile= adds the object to =TEST_LDFLAGS= and makes every binary depend on it, so a custom link rule that uses =$(TEST_LDFLAGS)= gets it too. =/editor-tools/desktop-guard= fails (or the test does not link) if the guard is missing. A test that must really start a program unsets the variable around that one call, as =test-editor-tools= does. Since 0.9.2.

Frame-time benchmarks live in =bench/= (=make -C bench run=); see [[file:performance.org][Performance]].

*** GPU tests, editor runs and screenshots
:PROPERTIES:
:CUSTOM_ID: testing-xvfb
:END:
Suites that open a window (GPU tests, editor app tests, examples) need a display. Run them on a private Xvfb with =build-aux/xrun.sh=, never on your desktop session:

#+begin_src sh
build-aux/xrun.sh make test                                  # the whole suite with a display
build-aux/xrun.sh -t 300 tests/build/release/tests/test-pbr  # one suite, killed after 5 minutes
build-aux/xrun.sh build/release/lrgeditor --width 1920 --height 1080 ~/games/demo
#+end_src

The wrapper starts a 1920x1200 Xvfb with =-noreset= (otherwise a second window in the same process fails with "X11: Failed to open display"), forces X11 for GLFW, and gives the command a short =XDG_RUNTIME_DIR= and throwaway =XDG_CONFIG_HOME=, =XDG_DATA_HOME= and =XDG_CACHE_HOME=, so a run never changes your =~/.config/libregnum/editor.yaml= (=-k= keeps the real directories). Screenshots for docs and reviews are taken at 1920x1080 (=lrgeditor --width 1920 --height 1080=, =lrgeditorctl screenshot FILE --window=); AGENTS.md has a complete scripted recipe including dark/light themes. Fedora package: =xorg-x11-server-Xvfb= (plus =xdotool= for =make test-editor-x11=).

** Versioning
:PROPERTIES:
:CUSTOM_ID: versioning
:END:
The release version is =VERSION_MAJOR=, =VERSION_MINOR= and =VERSION_MICRO= in =config.mk=; it is compiled in as =LRG_VERSION_STRING= / =LRG_VERSION_*= (=lrg-version.h=) and written to the =.pc= file. Every release on master is an annotated tag =v<MAJOR>.<MINOR>.<MICRO>= on the commit that sets it, starting at =v0.1.0=. Micro bumps for fixes and small changes that alter the build, minor for major features or compatibility breaks; the full rules are in =AGENTS.md= ("Versioning"). =API_VERSION= (GIR namespace, =libregnum-1.pc=) and =SO_VERSION= are independent of the release version.

The bundled graylib (=deps/graylib=) follows the same scheme and always shares libregnum's MAJOR.MINOR: libregnum =v0.2.x= ships graylib =v0.2.x=, and only the micro versions move independently. =make test= checks it (=tests/test-version-lockstep.sh=).

To run tests manually:

#+begin_src sh
cd tests
LD_LIBRARY_PATH="../build/release/lib" ./test-engine --tap
#+end_src

** Cross-Compilation
:PROPERTIES:
:CUSTOM_ID: cross-compilation
:END:
Libregnum builds for Windows on x86_64 (=make WINDOWS=1=), Linux on aarch64 (=make ARM64=1=) and Android on arm64-v8a (=make ANDROID=1=) from the same checkout. Each target has its own build directory, so cross builds never disturb the native one:

| Target          | Release directory              | Debug directory              |
|-----------------+--------------------------------+------------------------------|
| native          | =build/release=                | =build/debug=                |
| =windows-amd64= | =build/release-windows-amd64= | =build/debug-windows-amd64= |
| =linux-arm64=   | =build/release-arm64=         | =build/debug-arm64=         |
| =android-arm64= | =build/release-android-arm64= | =build/debug-android-arm64= |

The [[file:cross-compile.org][Cross-Compilation Guide]] covers the target model, the toolchains, testing and adding a target.

** Build System Details
:PROPERTIES:
:CUSTOM_ID: build-system-details
:END:
Libregnum uses GNU Make with a three-file structure:

- *Makefile* - Main build orchestration
- *config.mk* - Configuration variables
- *rules.mk* - Build rules and helper functions

The build system is modeled after graylib's proven pattern.

Two more pieces decide the target:

- *build-aux/mk/target.mk* - resolves the target (=LRG_TARGET=, the =WINDOWS=/=ARM64=/=ANDROID= switches) and the build directory suffix. Cheap (only =uname=); =config.mk= includes it first, so =tests/=, =examples/= and =bench/= agree with the root.
- *build-aux/mk/targets/<target>.mk* - one profile per cross target: toolchain, =TARGET_PLATFORM=, forced feature defaults, test runner. =config.mk= reads it after its tool defaults.

Include order: =Makefile= → =config.mk= → =target.mk= → (cross only) =targets/<target>.mk= → the rest of =config.mk= → =rules.mk=.

*** Build-system tests
:PROPERTIES:
:CUSTOM_ID: build-system-tests
:END:
=make test-build-system= checks the build system itself, without compiling: target resolution and build directories for every target and spelling (=tests/test-build-targets.sh=), what each clean goal removes (=tests/test-build-clean.sh=), ShellCheck on the build scripts, and the native no-regression gate. The gate (=tests/test-native-unchanged.sh=, also =make test-native-unchanged [BASE=ref]=) hard-links the tree, puts every file that differs from the base ref back to its base content (submodules included) and diffs =make -Bn= for =all=, =tests= and =examples=; it needs a native =make all= first. =make test= runs the first three as part of the suite.
